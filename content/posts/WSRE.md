# SRE简介

站点可靠性工程是一门工程专业，致力于持续帮助组织实现系统、服务和产品的可靠性级别。——本·特雷诺·斯洛斯

SRE 最核心的一词是“可靠性”，定义中说的不是“适当性能级别”、“适当效率级别”、“适当稳定性级别”或“达到适当收入级别”， 而是“适当可靠性级别”。如果应用程序没有正常运行（即如果它在客户需要访问它时无法运行或如果它不可靠），这对任何人都没有任何好处，尤其是对企业。缺少可靠性可能会（在信誉、经济、合同、士气等方面）对企业造成实际危害。

站点可靠性工程是一门工程专业，致力于持续帮助组织实现系统、服务和产品的可靠性级别。据 SRE 领域的重要观察，必须 100% 可靠的系统和服务寥寥无几。 值得注意的例外是，航空、医疗设备等生死攸关的行业。可靠性级别必须与业务需求保持一致，且切实可行。 例如，我们的客户可能通过不是 100% 可靠的网络连接到你（假设 90% 的时间都是）。 花费精力和金钱来确保服务 95% 的可靠性显然浪费时间和金钱。 建议实现系统、服务和产品的适当可靠性级别。

我们在继续之前需要重点强调的定义中的最后一个词是“持续”。 “持续”是指人员的角色。 创建可持续的操作实践至关重要。 人员生成可靠的系统、服务和产品。 **如果我们不采取措施确保我们的工作是可持续的。 如果我们每天凌晨 3:00 把员工叫醒交付他们工作，不给他们和家人在一起的时间。 如果他们没有机会花时间照顾自己。 那么，他们就不可能构建可靠的系统。** SRE 认为我们非常有必要实施一种长期可持续的操作实践，以便我们的员工能够在工作中发挥最大才能。

DevOps 可以理解为一种让开发和运维更紧密合作的软件交付方式。过去开发人员主要负责写代码，运维人员主要负责部署和维护系统，两边往往彼此独立。这样很容易出现“开发只管功能，运维只管稳定”的问题。DevOps 想解决的就是这种割裂，让开发、测试、部署和运维尽量形成一条连续的流程，并通过 CI/CD、自动化测试、自动部署等方式提高软件交付效率。

SRE，也就是站点可靠性工程，更关注系统上线之后如何长期稳定运行。它的核心思想是把传统运维中的问题当成工程问题来解决。例如，系统出现故障时，不只是依赖运维人员手动处理，而是考虑能不能通过监控、自动恢复、容量规划等方式提前发现和自动解决。SRE 还会用 SLI、SLO、Error Budget 等指标来明确“系统到底需要多可靠”。

两者最大的区别在于关注重点不同。DevOps 更关心“开发和运维怎么更好地协作，以及软件怎么更快、更顺利地上线”；SRE 更关心“系统上线之后怎么保持可靠，出了故障怎么快速恢复，以及怎么减少人工运维”。因此，DevOps 更像一种文化和工作方式，而 SRE 更像一套比较具体的工程方法。

不过两者并不是互相替代的关系。它们都强调自动化、监控、持续改进和减少人为失误，所以实际工作中经常会一起出现。一个已经实行 DevOps 的团队，通常也更容易进一步引入 SRE 的做法。**DevOps 主要解决“怎么把软件交付好”，SRE 主要解决“怎么让软件运行好”。**

假设你正计划要将一项新服务投入生产，可能是已构造的服务，也可能是仍在计划过程当中的服务。 在此过程中，务必要对所需的可靠性做出一些决定。 如果不是所有代码都是你自己编写的，请与编写相应代码的开发人员共同做出这些决定（这一点至关重要）。

要做出的第一个决定是，应该用什么作为服务运行状况的指标（即“服务级别指标 (SLI)”）？ 这个问题的另一种问法是，“如何判断服务何时在运行且运行良好？”。 有很多方法可以跟踪 SLI，我们稍后会详细探讨一些方法。 但是，以下指标是很典型的：

* 成功与失败度量标准： 服务是否在某个时间间隔内成功完成一定比例的操作？
* 计时度量值： 我们在某个时间阈值内是否返回答案？
* 吞吐量度量值： 我们处理了一定量的数据吗？

SLO（Service Level Objective，服务级别目标）是团队根据服务运行指标设定的可靠性目标。例如，可以规定一天内的故障率不超过 20%。这里使用 20% 这样较大的数值，一方面便于理解和计算，另一方面也体现了 SRE 中对开发速度与运行稳定性之间平衡的考虑：在满足可靠性要求的同时，为持续交付、快速迭代和敏捷开发保留一定的调整空间。后续还可以进一步限定统计范围，例如哪些用户受到影响、错误率针对部分用户还是大多数用户等，从而使 SLO 的定义更加精确。

必须能够在监视系统中准确度量和表示 SLO。 这应该是一个客观且易于理解的服务可靠性目标。 多大的数字才够好呢？ 不得有下面这样的说辞：“好吧，我认为这项服务在过去一周左右的时间里一直没问题，但具体怎样很难说”。 服务要么实现 SLO，要么没有实现。 数据应该很明确。 如果服务没有实现 SLO（特别是在一段时间内反复这样），表示服务出现了问题，需要进行解决。

误差预算（Error Budget）是由 SLO 推导出来的“允许不可靠空间”。如果某项服务的 SLO 是 80% 可用性，那么理论上的误差预算就是 100% - 80% = 20%。这 20% 表示：只要整体可靠性仍然满足 SLO，服务可以在这部分范围内承担一定的故障、发布风险或升级带来的不稳定。

误差预算的意义在于，它为开发速度和系统稳定性之间提供了一个可以量化的平衡。例如，新版本上线后导致 10% 的额外故障时间，只要仍然没有超出 20% 的误差预算，就可以认为整体仍处于可接受范围内。因此，团队可以把一部分误差预算用于发布新功能、升级系统和快速迭代。

如果服务可靠性下降到 SLO 以下，例如目标是 80%，实际却只有 60%，就意味着误差预算已经耗尽甚至透支。此时团队通常会减少或暂停新的功能发布，把更多工程资源投入到稳定性、故障排查和可靠性改进中，直到服务重新恢复到目标水平。

因此，误差预算可以看作一种反馈机制：预算充足时，团队可以更积极地发布和迭代；预算接近耗尽时，就应更加保守；预算耗尽后，则优先修复可靠性问题。它把“到底该继续发版本，还是先解决稳定性问题”从主观争论转化成了基于 SLO 的工程判断。

事后调查（Postmortem）是对重大故障或异常事件进行回顾分析，目的是弄清楚故障为什么发生、哪些环节失效，以及今后如何避免类似问题再次出现。SRE 特别强调“无责备事后调查”，也就是分析重点放在系统、流程和信息设计上，而不是追究某个具体人员的责任。

无责备并不意味着忽视人的操作，而是进一步追问：为什么现有流程会允许一次操作演变成故障？当事人在当时缺少了什么信息？哪些提示或机制可能让他做出了错误判断？系统是否应该增加自动检查、权限限制、回滚机制或其他保护措施？核心目标是让系统本身变得更不容易出错。

这种做法背后的逻辑是，如果每次事故都优先寻找“谁犯了错”，员工以后就会更倾向于隐瞒问题、避免操作和拒绝尝试，从而让组织失去真正学习和改进的机会。相反，良好的事后调查会把故障转化为经验，通过持续改进流程和技术，让整个系统越来越可靠。

因此，SRE 把故障看作学习机会。每次事故都应该形成“发生故障—分析原因—改进系统—降低未来风险”的反馈循环，这也是 SRE 持续提升可靠性的核心机制之一。

Toil 是 SRE 中专门用来描述低价值重复性运维工作的概念。它通常具有手动、重复、可自动化、会随系统规模增长而增加等特点，而且完成这些工作并不会让系统得到长期改善。例如，反复重启进程、定期手动重置配置、人工创建账号或分配磁盘空间，都属于典型的 Toil。

Toil 的关键问题不在于工作本身是否困难，而在于它需要不断重复投入人力，却不会形成长期收益。即使这些工作通过工单系统被规范地记录和处理，只要最终仍然需要工程师一次次手动完成，它依然属于 Toil。

SRE 会尽可能减少或消除 Toil，其中最重要的手段之一就是自动化。通过把重复操作交给脚本、平台或自动化系统完成，可以让工程师把时间投入到架构改进、可靠性优化和工具建设等更有长期价值的工作中。不过，并不是所有 Toil 都必须立即消除，是否值得自动化仍要结合成本和优先级判断。

SRE 团队需要在“日常运维”和“长期工程改进”之间保持平衡。工程师不能把全部时间都用在处理告警、响应故障和清理工单上，还必须留出足够的时间编写代码、建设自动化工具、减少 Toil，并通过工程项目持续提高系统可靠性。

Google SRE 模型中常引用的原则是：**操作性工作最好不要长期超过团队总时间的 50%**。这里的 50% 并不是严格标准，而是一个经验性的上限，用来提醒团队必须为自动化和可靠性建设保留足够的工程时间。

在严重故障期间，SRE 团队短时间内把几乎全部精力投入救火是正常的；但如果这种状态长期持续，说明团队已经陷入被动运维：大量时间用于处理重复问题，却没有时间从根源上消除这些问题。这不仅容易造成工程师疲劳，也会使系统可靠性难以真正提高。

因此，SRE 强调形成一个正向循环：控制日常运维负担，把节省下来的时间投入自动化和可靠性改进，再进一步减少未来的运维负担。同时，也需要合理分配值班和告警压力，避免少数成员长期承担过重的响应任务。

# 可靠性核心思路

可靠性（Reliability）是指系统在发生故障、异常或中断时，仍然能够持续提供预期功能的能力。一个可靠的系统通常需要同时具备韧性（Resiliency）、可恢复性（Recoverability）和可用性（Availability）。韧性强调系统在部分组件发生故障时仍能继续运行；可恢复性强调当故障超过系统的承受能力后，能够在约定时间内恢复服务；可用性则强调用户能否在承诺的时间范围内，以预期的质量访问服务。

在分布式系统中，故障几乎是不可避免的。某些组件可能发生故障，而其他组件仍然正常工作，因此系统设计不能建立在“不会出错”的假设上。真正需要考虑的是：系统能否提前发现问题、限制故障影响范围，并在必要时快速恢复，避免局部故障最终影响用户体验和业务目标。

可靠性不能只依赖某一个环节，而应同时体现在应用代码、基础设施和日常运维中。例如，应用本身需要具备异常处理和降级能力，基础设施需要考虑冗余和故障切换，运维则需要具备监控、告警和恢复机制。这些设计都应该服务于业务需求，而不能为了提高可靠性随意改变系统原本要实现的业务目标；如果必须做出取舍，就应该把它视为明确的架构权衡。

因此，可靠性设计应该贯穿整个开发生命周期，从设计阶段开始考虑系统可能出现的故障，并根据实际业务要求选择合适的方案。设计原则和可靠性检查清单的作用，就是帮助团队提前考虑这些问题，而不是等系统上线后出现事故再被动补救。对于普通系统，可靠性不足可能造成服务中断和经济损失；对于关键系统，严重的可靠性问题甚至可能影响安全。

## 面向业务需求进行设计

可靠性设计应从业务需求出发，而不是凭经验猜测。需要先明确系统范围、用户增长、服务承诺、可接受的用户体验以及成本和技术约束，再根据这些要求选择合适的可靠性方案。

| 设计方法                                                                                                     | 通俗解释                                                           | 作用                                                             |
| ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------ | ---------------------------------------------------------------- |
| 明确解决方案的范围和深度，包括需要多高的韧性、恢复能力、可观测性和简洁性，并确定成本、合规、地域、延迟等约束 | 先搞清楚“这个系统到底需要做到什么程度”，不要一开始就按最高标准设计 | 明确“做到什么程度就足够”，避免目标模糊导致反复修改设计、浪费成本 |
| 将业务目标转化为架构上的权衡，综合考虑成本、工程复杂度、安全和运维负担                                       | 每提高一点可靠性，通常都要付出额外成本，所以必须权衡               | 让业务方理解可靠性要求背后的代价，从而形成现实可行的目标         |
| 优先针对关键用户流程定义可靠性目标，而不是只关注整体 uptime                                                  | 不要只看“网站有没有活着”，而要看用户最重要的操作能不能完成         | 让可靠性直接对应真正有业务价值的功能                             |
| 按时间尺度考虑需求，例如上线时的用户量以及未来用户是线性、快速还是不确定增长                                 | 不只考虑现在能不能跑，还要考虑未来规模扩大后是否还能稳定运行       | 既满足当前需求，又避免未来因为增长而大规模重构                   |
| 考虑无法完全控制的外部依赖，例如统一基础设施、安全要求、网络策略和平台限制                                   | 系统的可靠性不只取决于自己，还取决于外部平台和依赖服务             | 确保 SLO、RTO、RPO 等目标现实可行，避免做出无法兑现的承诺        |

*关键词*

* **关键用户流程（Critical User Flow）**：用户完成核心业务目标所经过的一整条流程，例如“登录 → 选择商品 → 下单 → 支付”。
* **Uptime**：系统处于可用状态的时间比例。
* **SLO**：服务级别目标，用来规定系统应达到的可靠性水平。
* **RTO**：Recovery Time Objective，恢复时间目标，即故障后允许多长时间恢复服务。
* **RPO**：Recovery Point Objective，恢复点目标，即最多允许丢失多长时间范围内的数据。
* **架构权衡（Trade-off）**：为了获得某种好处，需要接受其他方面的代价，例如更高可靠性通常意味着更高成本和复杂度。

## 面向韧性进行设计

韧性（Resilience）强调：即使部分组件发生故障、平台中断、性能下降或资源不足，系统仍然能够以完整或降级形式继续提供服务。设计时应默认故障一定会发生。

| 设计方法                                                 | 通俗解释                                                 | 作用                                                       |
| -------------------------------------------------------- | -------------------------------------------------------- | ---------------------------------------------------------- |
| 区分关键路径组件和允许降级的非关键组件                   | 先判断哪些组件一坏整个业务就不行，哪些坏了只是体验差一点 | 将可靠性资源集中到真正重要的组件上，避免过度设计           |
| 找出潜在故障点，特别是关键组件，并分析对用户流程的影响   | 提前想清楚“哪里可能坏、坏了会影响多大范围”               | 可以评估故障类型、严重程度和影响范围，据此设计错误处理机制 |
| 通过合理的设计模式、模块化和故障隔离建立系统自我保护能力 | 一个模块出问题时，不要让问题继续传到其他模块             | 防止故障向下游传播，缩小故障范围                           |
| 让关键组件具备横向扩展能力，并考虑不同区域的容量限制     | 流量变大时，可以增加更多实例一起分担压力                 | 应对突发流量和容量变化，也能缓解单一区域资源不足           |
| 在基础设施、数据、服务、运维和人员等多个层次建立冗余     | 重要东西不要只有一份，避免一个点坏了整个系统就停         | 减少单点故障，提高整体可用性                               |
| 适当进行资源超配，为系统保留额外容量                     | 平时不要把资源用到极限，要留一点余量应对突发情况         | 在实例故障或资源异常增长时提供缓冲，为扩容和修复争取时间   |

*关键词*

* **Resilience（韧性）**：系统在发生部分故障时，仍然能够继续提供服务的能力。
* **关键路径（Critical Path）**：完成核心业务流程时必须经过的一组组件，其中任意关键组件失败都可能导致整个流程失败。
* **Graceful Degradation（优雅降级）**：部分功能失效时，系统主动降低功能或服务质量，但仍保持核心功能可用。
* **Blast Radius**：某个故障能够影响的范围。设计目标通常是尽量缩小故障影响范围。
* **故障隔离（Fault Isolation）**：通过架构设计阻止一个组件的故障扩散到其他组件。
* **横向扩展（Scale Out）**：通过增加更多服务器或实例来提高处理能力，而不是单纯增强单台机器性能。
* **冗余（Redundancy）**：为关键组件准备多个副本或替代路径，避免单点故障。
* **单点故障（Single Point of Failure）**：某个组件一旦失效，就会导致整个系统或核心功能停止。
* **资源超配（Overprovisioning）**：提前准备超过正常需求的计算、存储或网络资源，为故障和流量突增提供缓冲。

## 面向恢复进行设计

再强的韧性也无法处理所有故障。因此还必须考虑 Recovery：当故障已经超过系统自身的容错能力时，如何在规定的恢复目标内重新提供服务，并恢复正确的数据状态。

| 设计方法                                                     | 通俗解释                                                   | 作用                                                 |
| ------------------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------------- |
| 制定结构化、经过测试、有文档记录，并与恢复目标一致的恢复计划 | 真出大故障时不能临时想怎么办，要提前把恢复步骤写清楚并测试 | 在事故发生时能够快速、按流程恢复，减少业务和声誉损失 |
| 定期进行组件、数据、故障切换和故障回切演练                   | 恢复方案不能只写在文档里，还要真正演练过                   | 验证恢复流程是否真的可用                             |
| 确保所有有状态组件的数据都能在恢复目标内修复                 | 服务重新启动还不够，数据库里的数据也必须能恢复             | 利用可信恢复点和备份把系统恢复到正常状态             |
| 使用不可变并保持事务一致性的备份                             | 备份本身也要可靠，不能恢复以后发现数据还是坏的             | 防止备份被篡改，并保证恢复数据的一致性               |
| 建立自动自愈能力                                             | 一些常见故障可以让系统自己检测、自己恢复                   | 减少人工干预和人为错误，缩短恢复时间                 |
| 将无状态组件设计成不可变、可随时创建和销毁的临时单元         | 与其在坏掉的机器上反复修，不如直接重新创建一个干净实例     | 提高部署一致性和可重复性，并减少恢复过程中的中断     |

*关键词*

* **Recovery（恢复能力）**：当系统已经无法继续正常工作时，将服务恢复到可接受状态的能力。
* **Stateful Component（有状态组件）**：内部保存持久数据或状态的组件，例如数据库。
* **Stateless Component（无状态组件）**：自身不依赖本地持久状态，可以比较容易地被替换或重新创建。
* **Failover（故障切换）**：主系统故障后，将业务切换到备用系统。
* **Failback（故障回切）**：原系统恢复后，再把业务从备用系统切回。
* **Immutable Backup（不可变备份）**：创建后不能被随意修改或删除的备份。
* **事务一致性（Transactional Consistency）**：备份或恢复的数据保持完整的业务状态，不会出现部分操作成功、部分操作丢失的情况。
* **Self-healing（自愈）**：系统检测到故障后自动执行重启、替换、切换等恢复操作。
* **Ephemeral Unit（临时单元）**：可以随时创建和销毁的实例，例如容器实例。

## 面向运维进行设计

可靠性工作应该尽量 Shift Left，即提前到开发和测试阶段，而不是等生产环境发生事故之后再处理。需要尽早测试故障，同时通过可观测性、诊断、告警和自动化支撑生产环境的可靠运行。

| 设计方法                                                               | 通俗解释                                                 | 作用                                                     |
| ---------------------------------------------------------------------- | -------------------------------------------------------- | -------------------------------------------------------- |
| 建立能够关联遥测数据的可观测系统                                       | 系统出了问题后，要能看见发生了什么，而不是只能靠猜       | 能确定哪里故障、何时发生、为什么发生，并观察完整用户流程 |
| 预测潜在故障和异常行为，并建立有优先级、可操作的告警                   | 告警不是越多越好，而是要及时指出真正需要工程师处理的问题 | 让 SRE 快速处理正在发生的事故，也可以提前处理潜在故障    |
| 在预生产和生产环境中主动模拟故障                                       | 主动制造故障，看看系统是否真的能按设计继续运行或恢复     | 验证真实恢复能力、降级机制和可靠性阈值                   |
| 在设计阶段考虑自动化，并尽可能自动化测试、部署和运维                   | 重复、标准化的事情尽量交给机器完成                       | 减少人为错误，提高不同环境和操作之间的一致性             |
| 评估日常操作对系统稳定性的影响，例如版本升级、安全审计、组件升级和备份 | 很多故障不是机器自己坏了，而是正常维护时改坏的           | 避免正常运维操作反而成为生产事故来源                     |
| 持续从真实生产事故中学习                                               | 每次出事故都应该留下改进措施，而不是修好就算了           | 找出设计和运维缺陷，并利用事故经验持续改进系统           |

*关键词*

* **Shift Left**：把测试、可靠性、安全等工作尽量提前到开发生命周期的前面阶段。
* **Observability（可观测性）**：根据系统产生的数据理解其内部运行状态的能力。
* **Telemetry（遥测数据）**：系统运行过程中自动采集的数据，例如日志、指标和调用链。
* **Metrics（指标）**：CPU 使用率、请求错误率、响应时间等数值数据。
* **Logs（日志）**：系统在运行过程中记录的事件和错误信息。
* **Traces（链路追踪）**：追踪一次请求在多个服务之间完整的调用过程。
* **Alert（告警）**：当系统达到某种异常条件时自动通知相关人员。
* **Pre-production（预生产环境）**：正式生产环境之前用于验证系统的环境，例如测试环境、预发布环境。
* **Incident（生产事故）**：已经对线上系统、用户或业务造成实际影响的故障事件。

## 保持简单

可靠性不意味着不断增加组件。系统越复杂，配置错误、组件交互和意外行为出现的可能性通常越高，因此应尽量减少没有必要的复杂性。不过也不能为了简单而形成新的单点故障，需要在简单与冗余之间保持平衡。

| 设计方法                                                                 | 通俗解释                                             | 作用                                               |
| ------------------------------------------------------------------------ | ---------------------------------------------------- | -------------------------------------------------- |
| 只有真正有助于实现业务目标时才添加新组件，并尽量保持关键路径精简         | 不要为了让架构“看起来高级”就不断增加服务和组件       | 减少关键故障点，同时让系统更容易实现、理解和管理   |
| 为代码、部署和运维流程建立统一标准并形成文档，尽可能通过自动验证强制执行 | 大家按同一套规则工作，减少因为个人习惯不同导致的问题 | 提高一致性，减少人为错误，也方便故障排查           |
| 判断理论上的设计方法是否真的适合实际业务场景                             | 理论上很先进的方案，不一定适合当前系统               | 避免过度细粒度和过度复杂设计造成额外依赖和维护负担 |
| 只编写足够满足需求的代码                                                 | 没必要为了可能永远不会发生的问题提前写大量复杂代码   | 减少资源浪费、数据流问题和代码缺陷                 |
| 优先利用平台已经提供并经过验证的功能和现成能力                           | 能用成熟方案解决的事情，就不要重新造一套             | 缩短开发时间，并复用已经验证过的可靠性实践         |

*关键词*

* **Critical Path（关键路径）**：完成核心业务所必须经过的组件和步骤。
* **Overengineering（过度设计）**：为了并不存在或不重要的问题，加入过多组件、机制和复杂性。
* **Standardization（标准化）**：为代码、部署、配置和运维制定统一规则。
* **Automated Validation（自动验证）**：使用工具自动检查代码、配置或流程是否符合标准。
* **Platform-provided Feature（平台能力）**：云平台、操作系统或基础设施已经提供的成熟功能，例如负载均衡、自动扩缩容、监控和备份。
* **Technical Complexity（技术复杂度）**：由于组件数量、依赖关系、配置和交互增加而带来的理解、维护和故障排查难度。

## 检查清单

这份 Checklist 用来检查一个系统的架构是否真正考虑了**可靠性、韧性和故障恢复能力**。核心思路是：先根据业务需求确定可用性和恢复目标，再据此选择基础设施和应用设计方案。可靠性不能只在系统上线之后考虑，而应该贯穿**设计、开发、测试和运维的整个生命周期**。每个架构决策都可能影响系统的可靠性，因此需要明确其中的权衡，而不是单纯堆叠高可用技术。

---

1. **RE:01 保持简单和高效**

**Focus your workload design on simplicity and efficiency.**

| 设计建议                                 | 通俗解释                                             | 作用                                               |
| ---------------------------------------- | ---------------------------------------------------- | -------------------------------------------------- |
| 让系统设计尽量保持简单，同时满足业务需求 | 不要为了“架构高级”加入大量实际上用不到的组件和技术   | 降低系统复杂度，减少配置错误、依赖问题和潜在故障点 |
| 使用实用而不是过度复杂的方案             | 能简单解决的问题就不要使用复杂方案                   | 降低开发、维护和故障排查成本                       |
| 在满足业务目标的前提下提高效率           | 简单并不意味着功能不足，而是在满足需求后不做多余设计 | 避免 Overengineering，让架构更容易理解和维护       |

**关键词**

* **Simplicity（简单性）**：尽量减少不必要的组件、依赖和逻辑。
* **Efficiency（效率）**：在满足目标的同时减少不必要的资源和工程投入。
* **Overengineering（过度设计）**：使用远超实际需求的复杂架构或技术方案。

---

2. **RE:02 识别并评估用户流和系统流**

**Identify and rate user and system flows.**

| 设计建议                           | 通俗解释                                           | 作用                               |
| ---------------------------------- | -------------------------------------------------- | ---------------------------------- |
| 找出系统中的用户流程和系统内部流程 | 不要只看“有哪些服务器”，还要看用户实际怎么使用系统 | 从完整业务流程角度分析可靠性       |
| 根据业务需求评估每条流程的重要程度 | 不同流程的重要性不一样，例如付款比查看推荐更重要   | 把可靠性资源优先投入真正重要的业务 |
| 建立关键性等级                     | 给不同流程分级，例如关键、重要、普通               | 为后续冗余、监控和恢复策略提供依据 |

**关键词**

* **User Flow（用户流）**：用户完成一个业务目标时经过的一系列步骤。
* **System Flow（系统流）**：系统内部组件之间完成某项功能时的数据或调用流程。
* **Criticality（关键性）**：某个流程对业务的重要程度。
* **Critical Flow（关键流程）**：一旦失败就会严重影响核心业务的流程。

例如：

```text
用户登录 → 搜索商品 → 加入购物车 → 下单 → 支付
```

这就是一条用户流程，其中：

```text
支付 > 推荐商品
```

因为支付失败会直接影响业务目标，而推荐失败通常只影响体验。

---

3. **RE:03 使用故障模式分析**

**Use Failure Mode Analysis (FMA) to identify potential failures.**

| 设计建议                 | 通俗解释                                 | 作用                     |
| ------------------------ | ---------------------------------------- | ------------------------ |
| 找出系统可能发生的故障   | 提前思考“什么东西可能坏”                 | 在事故发生前发现潜在风险 |
| 识别组件之间的依赖关系   | 一个组件坏了，可能会影响依赖它的其他组件 | 防止局部故障扩大         |
| 找出关键故障点           | 分析哪些组件一旦故障会产生严重影响       | 优先对高风险部分进行保护 |
| 针对不同故障制定缓解方案 | 不能只知道“会坏”，还要提前决定坏了怎么办 | 提高系统应对故障的能力   |

**关键词**

* **FMA（Failure Mode Analysis，故障模式分析）**：系统性分析“可能出现哪些故障，以及这些故障会产生什么影响”。
* **Failure Mode（故障模式）**：某个组件可能以什么方式失效。
* **Failure Point（故障点）**：系统中可能发生故障的位置。
* **Dependency（依赖）**：一个组件正常运行所依赖的其他组件或服务。
* **Mitigation（缓解措施）**：降低故障发生概率或影响程度的措施。

可以简单理解为：

> **先假设每个东西都有可能坏，然后问：它坏了会怎样？我们准备怎么办？**

---

4. **RE:04 定义可靠性和恢复目标**

**Define reliability and recovery targets.**

| 设计建议                           | 通俗解释                                         | 作用                           |
| ---------------------------------- | ------------------------------------------------ | ------------------------------ |
| 明确系统应该达到什么可靠性水平     | 不要只说“系统要稳定”，而要给出具体数字           | 让可靠性可以衡量               |
| 明确故障后需要多快恢复             | 系统挂了以后多久恢复才算可以接受                 | 指导灾难恢复方案设计           |
| 根据这些目标设计系统架构           | 先定目标，再决定要不要做冗余、备份、多区域等设计 | 避免盲目堆高可用技术           |
| 将可靠性指标作为系统健康模型的基础 | 系统是否健康，要根据提前定义的指标判断           | 让监控、告警和运维具有明确标准 |

**关键词**

* **Reliability Target（可靠性目标）**：系统需要达到的可靠性水平。
* **Availability Target（可用性目标）**：系统需要保持可用的时间比例。
* **SLO**：服务级别目标。
* **RTO**：Recovery Time Objective，允许的最大恢复时间。
* **RPO**：Recovery Point Objective，允许的数据损失范围。
* **Health Model（健康模型）**：通过一组指标判断系统当前是否处于正常状态的方法。

例如：

```text
SLO：99.9% 可用性
RTO：30 分钟
RPO：5 分钟
```

表示：

> 系统应该达到 99.9% 可用性；
> 真挂了以后最多 30 分钟恢复；
> 最多允许损失最近 5 分钟的数据。

---

5. **RE:05 建立不同层次的冗余**

**Add redundancy at different levels, especially for critical flows.**

| 设计建议                 | 通俗解释                                 | 作用                       |
| ------------------------ | ---------------------------------------- | -------------------------- |
| 为关键流程增加冗余       | 核心业务不要依赖唯一的一台机器或一个组件 | 防止单点故障               |
| 对计算资源进行冗余       | 一台服务器坏了，还有其他实例接管         | 保持服务继续运行           |
| 对网络等基础设施进行冗余 | 一条网络路径故障时，可以走其他路径       | 减少基础设施故障造成的中断 |
| 部署多个解决方案实例     | 不让系统只有唯一实例                     | 提高整体可用性和容错能力   |

**关键词**

* **Redundancy（冗余）**：准备多个能够完成同一功能的资源。
* **Single Point of Failure（单点故障）**：某个组件一旦失效，就会导致整个系统无法工作的情况。
* **Instance（实例）**：某个应用或服务正在运行的一个副本。
* **Critical Flow（关键流程）**：直接影响核心业务的用户或系统流程。

最简单的例子：

```text
只有一台服务器
        ↓
服务器挂了
        ↓
网站挂了
```

增加冗余后：

```text
服务器 A
服务器 B
服务器 C
    ↓
A 挂了
    ↓
B、C 继续服务
```

---

6. **RE:06 建立可靠的扩缩容策略**

**Implement a timely and reliable scaling strategy.**

| 设计建议                             | 通俗解释                                       | 作用                       |
| ------------------------------------ | ---------------------------------------------- | -------------------------- |
| 在应用、数据和基础设施层面考虑扩缩容 | 不只是服务器要能扩，数据库和应用本身也需要能扩 | 避免某一层成为性能瓶颈     |
| 根据真实或预测的使用量进行扩缩容     | 用户变多时增加资源，用户变少时减少资源         | 在可靠性和成本之间取得平衡 |
| 尽量减少人工操作                     | 不要等工程师发现服务器不够了才手动加机器       | 提高扩容速度并减少人为错误 |
| 确保扩容能够及时发生                 | 扩容太慢的话，资源增加之前系统可能已经挂了     | 应对突发流量               |

**关键词**

* **Scaling（扩缩容）**：根据负载增加或减少系统资源。
* **Scale Out（横向扩展）**：增加更多实例。
* **Scale In（横向缩减）**：减少实例。
* **Autoscaling（自动扩缩容）**：根据负载自动调整资源数量。
* **Usage Pattern（使用模式）**：用户访问量随时间变化的规律。

例如：

```text
平时：5 台服务器

流量突然增加
        ↓
自动扩容
        ↓
20 台服务器

流量恢复正常
        ↓
自动缩容
        ↓
5 台服务器
```

---

7. **RE:07 建立自我保护和自愈能力**

**Implement self-preservation and self-healing measures.**

| 设计建议                 | 通俗解释                                         | 作用                       |
| ------------------------ | ------------------------------------------------ | -------------------------- |
| 建立系统自我保护机制     | 系统发现异常时先保护自己，不要继续恶化           | 防止故障扩散               |
| 建立自动自愈能力         | 可以自动解决的问题就不要等待人工处理             | 缩短故障恢复时间           |
| 优先使用平台已有能力     | 云平台已经提供自动重启、故障切换等能力时优先使用 | 减少自己开发复杂机制的成本 |
| 使用经过验证的云设计模式 | 不要自己随便发明故障处理方式                     | 使用成熟经验提高可靠性     |

**关键词**

* **Self-preservation（自我保护）**：系统主动采取措施防止故障进一步扩大。
* **Self-healing（自愈）**：系统发现故障后自动恢复。
* **Cloud Pattern（云设计模式）**：经过大量实践验证的云架构设计方法。

例如：

```text
某个服务实例异常
        ↓
健康检查发现异常
        ↓
停止向它发送请求
        ↓
创建新的实例
        ↓
新实例重新加入服务
```

整个过程可以不需要人工参与。

---

8. **RE:08 使用混沌工程测试可靠性**

**Test resiliency and availability by applying chaos engineering.**

| 设计建议                         | 通俗解释                                   | 作用                               |
| -------------------------------- | ------------------------------------------ | ---------------------------------- |
| 主动制造故障进行测试             | 不要等真实事故发生才第一次看到系统怎么反应 | 验证系统是否真的具有韧性           |
| 测试系统是否能够承受组件故障     | 主动关掉服务器、网络或服务                 | 检查冗余和故障切换是否有效         |
| 测试高负载情况下是否可以扩容     | 人为制造流量高峰                           | 验证扩缩容策略                     |
| 测试系统是否可以在目标时间内恢复 | 故意制造中断，再观察恢复时间               | 验证 RTO、RPO 等目标是否真的能达到 |

**关键词**

* **Chaos Engineering（混沌工程）**：主动向系统注入故障，验证系统面对真实异常时的行为。
* **Fault Injection（故障注入）**：人为制造服务器、网络、磁盘、服务等故障。
* **Reliability Testing（可靠性测试）**：验证系统是否满足既定可靠性目标。
* **Resilience Testing（韧性测试）**：验证系统部分组件故障时是否仍能继续运行。

例如：

> 主动杀掉一台生产服务器，然后观察流量是否自动切换到其他服务器。

重点不是“故意把系统搞坏”，而是：

> **提前证明系统真的扛得住故障。**

---

9. **RE:09 建立灾难恢复计划**

**Implement structured, tested, and documented disaster recovery plans.**

| 设计建议                       | 通俗解释                               | 作用                           |
| ------------------------------ | -------------------------------------- | ------------------------------ |
| 建立结构化的灾难恢复方案       | 大规模故障发生以后，要有完整恢复流程   | 避免事故发生后临时决定怎么办   |
| 恢复方案必须经过测试           | 文档上写“可以恢复”不等于真的能恢复     | 验证实际恢复能力               |
| 将恢复方案形成正式文档         | 谁负责、怎么恢复、恢复顺序都应该写清楚 | 减少事故期间的混乱             |
| 恢复方案应满足既定恢复目标     | 恢复速度和数据损失必须符合 RTO、RPO    | 保证灾难恢复能力满足业务要求   |
| 既考虑单个组件，也考虑整个系统 | 不能只知道如何恢复一台服务器           | 应对区域级、平台级等大规模事故 |

**关键词**

* **DR（Disaster Recovery，灾难恢复）**：面对严重系统中断或灾难时恢复业务的完整方案。
* **Disaster Recovery Plan（灾难恢复计划）**：描述事故发生后如何恢复系统、数据和业务的正式流程。
* **Failover（故障切换）**：从故障系统切换到备用系统。
* **Failback（故障回切）**：原系统恢复后重新切回。
* **Recovery Drill（恢复演练）**：定期模拟灾难并实际执行恢复流程。

普通故障可能是：

```text
一台服务器挂了
```

而 Disaster Recovery 更关注：

```text
整个机房故障
整个区域故障
严重数据损坏
大规模网络中断
```

---

10. **RE:10 持续监控系统健康状态**

**Continuously measure and track system health.**

| 设计建议                   | 通俗解释                                   | 作用                       |
| -------------------------- | ------------------------------------------ | -------------------------- |
| 持续监控系统健康状态       | 不能等用户告诉你“网站挂了”才发现问题       | 尽早发现异常               |
| 监控各组件和关键流程       | 不只看单台服务器，还要看用户的完整业务流程 | 判断故障是否真正影响用户   |
| 使用 uptime 和可靠性指标   | 用数据判断系统是否满足可靠性目标           | 衡量 SLO 等目标是否实现    |
| 保存历史监控数据           | 监控数据不能看完就丢                       | 支持趋势分析和事故调查     |
| 确保监控数据可以快速访问   | 出事故后要马上能找到相关数据               | 帮助故障响应和根因分析     |
| 利用监控数据进行事故后分析 | 事故结束后回看当时系统发生了什么           | 支持 Postmortem 和持续改进 |

**关键词**

* **System Health（系统健康状态）**：系统当前是否正常完成预期功能的整体状态。
* **Reliability Indicator（可靠性指标）**：衡量系统可靠性的指标，例如可用率、错误率和延迟。
* **Uptime**：系统正常可用的时间比例。
* **Monitoring（监控）**：持续收集和观察系统运行状态。
* **Post-incident Analysis（事故后分析）**：故障结束后根据监控、日志等数据分析事故原因。
* **Retention（数据保留）**：保存历史监控数据，供之后查询和分析。

---

## 整体理解

这 10 条其实可以压缩成一个完整的可靠性设计流程：

```text
RE:01 先保持设计简单
        ↓
RE:02 找出哪些业务流程最重要
        ↓
RE:03 分析这些流程可能怎么坏
        ↓
RE:04 定义到底需要多可靠、多久恢复
        ↓
RE:05 给关键部分增加冗余
        ↓
RE:06 确保流量增加时能够及时扩容
        ↓
RE:07 让系统能够自我保护和自动恢复
        ↓
RE:08 主动制造故障，验证这些设计真的有效
        ↓
RE:09 如果发生严重灾难，要有完整恢复方案
        ↓
RE:10 持续监控，确认系统实际是否达到目标
```

也就是说，这份 Checklist 并不是 10 个彼此独立的要求，而是从：

> **明确业务 → 找出关键流程 → 分析故障 → 定目标 → 做冗余和扩容 → 自动恢复 → 主动测试 → 灾难恢复 → 持续监控**

构成了一套完整的可靠性设计思路。

# Azure

## 云计算基础

云计算（Cloud Computing）是通过互联网按需提供计算服务的模式，它把原本需要自行购买和维护的 IT 资源变成随用随取的服务。这里的计算服务既包括虚拟机、存储、数据库和网络等传统基础设施，也包括物联网（IoT）、机器学习（ML）和人工智能（AI）等能力。

### 云计算提供什么

| 服务类型         | 通俗解释               | 例子                   |
| ---------------- | ---------------------- | ---------------------- |
| Virtual Machines | 在云里运行一台虚拟电脑 | Windows / Linux 虚拟机 |
| Storage          | 在云里保存数据         | 文件、对象、备份       |
| Databases        | 使用云端数据库         | SQL、NoSQL             |
| Networking       | 提供网络连接和流量管理 | 虚拟网络、负载均衡     |
| IoT              | 连接和管理物联网设备   | 传感器、工业设备       |
| ML               | 提供机器学习能力       | 模型训练、预测         |
| AI               | 提供人工智能能力       | 语音、视觉、生成式 AI  |

### 为什么云计算和传统数据中心不同

传统数据中心受物理基础设施限制较大。企业突然需要更多计算资源时，通常要经历以下过程：

```text
评估需求
→ 购买服务器
→ 等待运输
→ 安装服务器
→ 配置网络
→ 部署系统
```

采购、运输、安装和配置可能耗时很久，而云计算允许企业通过平台直接申请资源：

```text
需要更多资源
→ 在云平台申请
→ 几分钟内获得资源
```

两种方式的差别在于，基础设施从“提前购买”变成了“按需获取”。

### 实际例子

假设一家零售公司准备进行大型季节性促销，预计活动期间访问量会突然增加。传统方式可能需要提前几个月购买额外服务器：

```text
购买服务器
↓
安装和配置
↓
促销期间使用
↓
促销结束
↓
大量服务器闲置
```

使用云计算时，企业可以根据活动进度调整资源：

```text
促销开始
↓
临时增加云计算资源
↓
处理高峰流量
↓
促销结束
↓
减少资源
```

这种做法既能更快应对流量变化，也能让成本更接近实际需求。

### 云计算带来的几个变化

| 变化                   | 通俗解释                         | 作用                                         |
| ---------------------- | -------------------------------- | -------------------------------------------- |
| On-demand Provisioning | 需要资源时再创建                 | 不必提前几个月购买服务器                     |
| Rapid Scaling          | 可以快速增加或减少资源           | 更容易应对流量变化                           |
| Faster Testing         | 可以快速创建测试环境             | 开发和测试速度更快                           |
| Faster Recovery        | 故障后可以快速重新创建或切换资源 | 提高恢复能力                                 |
| Global Reach           | 可以在世界不同地区部署服务       | 让服务更靠近用户                             |
| Regional Resilience    | 可以跨区域设计系统               | 一个区域出问题时，可以由其他区域继续提供服务 |

### 关键词

* **Cloud Computing（云计算）**：通过互联网按需提供计算资源和服务。
* **IT Infrastructure（IT 基础设施）**：运行信息系统所需要的计算、存储、网络等基础资源。
* **Virtual Machine，VM（虚拟机）**：通过软件模拟出来的一台完整计算机。
* **Storage（存储）**：用于保存文件和数据的资源。
* **Database（数据库）**：用于组织、保存和查询数据的系统。
* **Networking（网络）**：负责不同计算资源之间的通信。
* **IoT（Internet of Things，物联网）**：让各种物理设备连接到网络并交换数据。
* **ML（Machine Learning，机器学习）**：让计算机通过数据学习规律并进行预测或判断。
* **AI（Artificial Intelligence，人工智能）**：让计算机完成通常需要人类智能才能完成的任务。
* **Provisioning（资源预配）**：创建并准备计算资源，使其可以使用。
* **On-demand（按需）**：需要时再申请资源，而不是提前准备。
* **Scaling（扩缩容）**：根据负载增加或减少资源。
* **Global Reach（全球覆盖）**：利用云平台在多个国家和地区部署服务。
* **Regional Resilience（区域韧性）**：通过跨区域部署降低单一区域故障带来的影响。

### 本节总结

传统 IT 的资源准备流程是：

```text
传统 IT
先买资源
↓
安装和配置
↓
再使用
```

云计算则把流程改为：

```text
云计算
需要资源
↓
立即创建
↓
按需使用
↓
不用时释放
```

因此，云计算把 IT 基础设施从长期采购、固定容量的资产，变成了可以按需获取、快速扩展和及时释放的服务。

## 云计算共享责任模型（Shared Responsibility Model）

共享责任模型说明了云服务商与客户各自负责什么。传统本地数据中心的机房、服务器、网络、操作系统、应用和数据几乎都由企业管理；迁移到云之后，云服务商接管底层基础设施，客户仍要管理自己的数据和访问权限，操作系统、平台与应用等中间层则取决于使用的是 IaaS、PaaS 还是 SaaS。

---

### 1. 本地数据中心中的责任

在传统本地数据中心（On-Premises）中，企业需要负责几乎整个 IT 环境：

| 责任内容             | 通俗解释                                 | 作用                   |
| -------------------- | ---------------------------------------- | ---------------------- |
| 维护物理空间         | 机房、门禁、消防等都需要企业自己管理     | 保证服务器所在环境安全 |
| 负责电力和冷却       | 服务器供电、UPS、空调散热都要自己维护    | 保证硬件能够持续运行   |
| 维护物理服务器       | 服务器坏了需要自己维修或更换             | 保证计算资源可用       |
| 维护网络             | 交换机、路由器、线路等都由自己管理       | 保证设备之间能够通信   |
| 管理操作系统和软件   | 系统安装、版本升级和补丁都需要自己完成   | 保证软件环境正常和安全 |
| 管理应用、账号和数据 | 应用部署、用户权限和数据保护都由企业负责 | 保证业务系统和数据安全 |

因此，On-Premises 基本意味着所有责任都由企业自己承担。

---

### 2. 上云以后，责任开始分开

使用云计算后，客户无法直接接触的数据中心、供电、冷却、物理网络和服务器等底层设施会转由云服务商负责：

| 云服务商负责         | 通俗解释                       |
| -------------------- | ------------------------------ |
| Physical Security    | 数据中心的门禁、安保等物理安全 |
| Power                | 数据中心和服务器供电           |
| Cooling              | 服务器散热和机房温度控制       |
| Network Connectivity | 底层数据中心网络连接           |
| Physical Hardware    | 真正的物理服务器及相关设备     |

与此同时，客户仍然必须管理自己的数据、账号、身份和访问控制：

| 客户负责        | 通俗解释                   |
| --------------- | -------------------------- |
| Data            | 自己上传、创建和保存的数据 |
| Information     | 企业自己的业务信息         |
| Access Security | 谁能够访问系统和数据       |
| Accounts        | 用户和服务账号             |
| Identities      | 用户、服务和设备的身份     |

Microsoft 可以替客户维护服务器，却不能替客户决定“张三是否应该看到公司的财务数据”。

---

### 3. 有些责任取决于使用方式

部分责任会随云服务模式变化。以 SQL 数据库为例：

**使用云端托管 SQL 数据库**

如果直接使用云服务商提供的数据库服务：

```text
云服务商：
维护数据库平台
安装数据库补丁
维护底层服务器
维护操作系统

客户：
管理数据库中的数据
配置用户和权限
决定数据如何使用
```

这种情况下，数据库平台本身主要由云服务商维护。

**在虚拟机中自己安装 SQL Server**

如果先创建一台虚拟机，再自己安装 SQL Server：

```text
云服务商：
维护物理服务器
维护数据中心
维护底层物理网络

客户：
维护虚拟机操作系统
安装和更新 SQL Server
安装数据库补丁
配置数据库
维护数据库中的数据
```

同样是 SQL 数据库，采用不同的服务模式，责任划分也会完全不同。

---

### 4. 共享责任与 IaaS、PaaS、SaaS

共享责任模型与云服务模式直接相关，总体规律是：

```text
On-Premises → IaaS → PaaS → SaaS

客户负责的内容越来越少
云服务商负责的内容越来越多
```

| 服务模式    | 客户责任 | 云服务商责任                 | 通俗理解                                 |
| ----------- | -------- | ---------------------------- | ---------------------------------------- |
| On-Premises | 几乎全部 | 几乎没有                     | 什么都自己管                             |
| IaaS        | 较多     | 主要负责底层物理基础设施     | 云厂商给你基础设施，上面的东西大多自己管 |
| PaaS        | 中等     | 基础设施和平台主要由厂商负责 | 云厂商连运行平台都帮你维护               |
| SaaS        | 较少     | 大部分系统由厂商负责         | 直接使用厂商已经运行好的软件             |

越靠近 IaaS，客户越像在自行运维；越靠近 SaaS，客户越接近直接使用现成服务。

---

### 5. IaaS 中的责任

IaaS（Infrastructure as a Service）主要把底层物理基础设施交给云服务商。

| 云服务商负责 | 客户通常负责 |
| ------------ | ------------ |
| 数据中心     | 操作系统     |
| 物理服务器   | 操作系统补丁 |
| 电力与冷却   | 应用程序     |
| 物理网络     | 数据         |
| 底层基础设施 | 用户与权限   |

IaaS 可以理解为云厂商提供一台“云里的电脑”，但系统里安装什么、如何配置和维护，主要仍由客户负责。

---

### 6. PaaS 中的责任

PaaS（Platform as a Service）进一步把操作系统和运行平台交给云服务商维护，客户主要关注：

* 应用代码
* 业务逻辑
* 数据
* 用户
* 权限

云服务商主要负责：

* 物理基础设施
* 操作系统
* 平台运行环境
* 平台维护和补丁

PaaS 不只提供机器，还准备好应用运行的平台，因此开发人员可以少关注服务器和系统维护，把更多精力放在应用本身。

---

### 7. SaaS 中的责任

SaaS（Software as a Service）中，云服务商负责的内容最多。客户直接使用已经运行好的软件，不需要自己维护：

* 软件安装
* 操作系统
* 服务器
* 数据库基础设施
* 软件补丁
* 平台升级

客户仍然需要管理自己的数据和使用方式，包括：

* 自己的数据
* 用户账号
* 角色
* 权限
* 接入设备

SaaS 的软件已经由服务商运行，客户主要负责如何使用它。

---

### 8. 无论使用哪种云服务，始终由客户负责的内容

无论采用哪种云服务，信息与数据、终端设备、账号与身份始终由客户负责：

| 内容                    | 通俗解释                           |
| ----------------------- | ---------------------------------- |
| Information and Data    | 自己存储在云中的信息和数据         |
| Devices / Endpoints     | 允许连接到云环境的电脑、手机等设备 |
| Accounts and Identities | 用户、服务和设备的账号及身份       |

上云不会把数据、账号、身份和终端设备的责任转交给云服务商。

**关键词**

* **Information and Data（信息和数据）**：企业在云中创建、存储和处理的业务信息。
* **Endpoint（终端）**：连接云环境的电脑、手机等设备。
* **Identity（身份）**：用户、服务或设备在系统中的身份。
* **Account（账号）**：用来登录和访问系统的账户。

---

### 9. 无论使用哪种云服务，始终由云服务商负责的内容

云服务商始终负责客户无法直接接触的物理云基础设施：

| 内容                | 通俗解释                       |
| ------------------- | ------------------------------ |
| Physical Datacenter | 真正的数据中心和机房           |
| Physical Network    | 数据中心中的实体网络设备和线路 |
| Physical Hosts      | 真正运行云服务的物理服务器     |

资源进入云环境后，真正的机房、物理服务器和物理网络便不再由客户维护。

---

### 10. 根据服务类型决定的责任

下面这些责任会随着 IaaS、PaaS、SaaS 的不同而变化：

| 责任                | 为什么会变化                                        |
| ------------------- | --------------------------------------------------- |
| Operating Systems   | IaaS 通常由客户维护，PaaS / SaaS 更多由厂商维护     |
| Network Controls    | 不同服务模式允许客户控制的网络层级不同              |
| Applications        | IaaS / PaaS 中更多由客户负责，SaaS 中更多由厂商负责 |
| Identity and Access | 客户和厂商通常共同承担                              |
| Infrastructure      | 上云之后逐渐转移给云服务商                          |

**Identity and Access 为什么是共享责任**

以 PaaS 或 SaaS 中的身份与访问为例，云服务商负责：

```text
运行认证平台
维护认证服务
维护底层身份基础设施
```

客户则负责：

```text
创建哪些用户
给用户什么角色
配置什么权限
制定什么访问策略
```

在 Microsoft Entra ID 中，Microsoft 负责身份平台的运行，企业负责决定谁能登录以及登录后可以执行哪些操作。

---

### 关键词

* **Shared Responsibility Model（共享责任模型）**：云服务商与客户共同承担云环境中的管理、安全和运维责任。
* **On-Premises（本地部署）**：服务器和基础设施由企业自己拥有和维护。
* **Cloud Provider（云服务商）**：提供云基础设施和服务的厂商，例如 Microsoft Azure。
* **Consumer / Customer（客户）**：使用云服务的组织或个人。
* **IaaS（Infrastructure as a Service）**：基础设施即服务。
* **PaaS（Platform as a Service）**：平台即服务。
* **SaaS（Software as a Service）**：软件即服务。
* **Identity and Access Management，IAM（身份与访问管理）**：管理用户身份以及用户能够访问哪些资源。
* **Authentication（认证）**：确认“你是谁”。
* **Authorization（授权）**：确认“你能够做什么”。
* **Role（角色）**：一组预先定义好的权限。
* **Policy（策略）**：用于规定访问和使用规则的配置。
* **Patch（补丁）**：修复软件漏洞、Bug 或安全问题的软件更新。

---

### 本节总结

共享责任会随着服务模式变化：

```text
On-Premises
客户几乎什么都负责
        ↓
IaaS
云服务商接管物理基础设施
        ↓
PaaS
云服务商进一步接管操作系统和平台
        ↓
SaaS
云服务商连应用本身也主要负责
```

客户承担的责任依次减少：

| 模式        | 客户责任 |
| ----------- | -------- |
| On-Premises | 最多     |
| IaaS        | 较多     |
| PaaS        | 较少     |
| SaaS        | 最少     |

无论采用哪种模式，客户始终负责数据、身份、账号和终端设备，云服务商始终负责物理数据中心、物理网络和物理服务器。共享责任模型并不表示责任消失，而是随着 On-Premises → IaaS → PaaS → SaaS，越来越多底层责任从客户转移到云服务商。

## 云计算部署模型（Cloud Models）

云模型说明云资源以什么方式部署、由谁使用以及资源属于谁，主要分为三种：

* Private Cloud（私有云）
* Public Cloud（公有云）
* Hybrid Cloud（混合云）

Multicloud（多云）也很常见，但它描述的是同时采用多个公有云平台，与三种基本部署模型不是同一个分类维度。公有云向多个客户开放，私有云只供一个组织使用，混合云则把公有云和私有云连接起来。

---

### 1. Private Cloud（私有云）

私有云是只供一个组织使用的云环境，可以看作传统数据中心云化后的形态。它仍然服务于单一组织，但资源管理方式更接近云计算，可以部署在企业自己的数据中心、其他专用数据中心，也可以交给第三方托管：

* 建在企业自己的本地数据中心
* 建在其他专用数据中心
* 甚至由第三方帮企业托管

| 特点                                   | 通俗解释                                 | 影响                       |
| -------------------------------------- | ---------------------------------------- | -------------------------- |
| 资源只属于一个组织                     | 不和其他客户共享核心资源                 | 控制能力更强               |
| 企业对资源和安全拥有完整控制权         | 网络、安全策略、硬件配置等都可以自己决定 | 更容易满足特殊安全要求     |
| 数据不会和其他租户放在同一个共享环境中 | 更容易进行严格的数据隔离                 | 适合部分高安全、高合规场景 |
| 需要自己购买硬件                       | 服务器等基础设施不能直接按需从公共云获取 | 初始投入通常更高           |
| 企业负责硬件维护和升级                 | 服务器坏了、需要升级都要自己处理         | 运维负担更重               |
| 公有云的一些优势会减少                 | 扩容速度、按需使用等能力可能不如公有云   | 灵活性通常较低             |

私有云就是公司专用的一套云。例如，一家银行可能因为安全、监管或数据要求，不希望核心系统运行在共享公有云中，因此建立自己的私有云。

**关键词**

* **Private Cloud（私有云）**：只供单一组织使用的云环境。
* **Dedicated Resources（专用资源）**：资源专门分配给某个组织，而不是和其他客户共同使用。
* **Tenant（租户）**：使用云平台资源的一个独立客户或组织。
* **On-site / On-premises（本地）**：资源部署在企业自己的场地或数据中心。
* **Control（控制权）**：企业能够直接决定硬件、网络、安全和配置方式的程度。

---

### 2. Public Cloud（公有云）

公有云由第三方云服务商建设、运营和维护，个人或组织通常都可以购买和使用，其中 Microsoft Azure 就是公有云平台。

| 特点                               | 通俗解释                                 | 影响                     |
| ---------------------------------- | ---------------------------------------- | ------------------------ |
| 云平台由第三方服务商建设和管理     | 客户不用自己建设数据中心                 | 大幅减少基础设施维护工作 |
| 大量客户共同使用云平台             | 云厂商把庞大的基础设施提供给很多客户使用 | 可以形成规模效应         |
| 不需要为了扩容提前购买硬件         | 需要更多资源时直接申请                   | 扩容速度快               |
| 应用可以快速创建和删除             | 需要时开，不需要时关                     | 非常灵活                 |
| 按实际使用量付费                   | 用多少资源通常付多少费用                 | 避免大量闲置基础设施     |
| 客户不能完全控制底层资源和物理安全 | 机房、物理服务器等由云厂商管理           | 控制权比私有云低         |

云厂商建设和维护大型平台，再把资源按需提供给大量客户。企业需要 100 台服务器时，可以直接在 Azure 上创建虚拟机，不必自行采购 100 台实体服务器。

**关键词**

* **Public Cloud（公有云）**：由第三方云服务商运营，并向多个客户提供服务的云环境。
* **Cloud Provider（云服务商）**：建设和运营公有云的企业。
* **Provisioning（资源预配）**：创建并准备云资源。
* **Deprovisioning（资源释放）**：删除或停止不再需要的云资源。
* **Capital Expenditure，CapEx（资本支出）**：提前购买服务器、机房等长期资产所需要的大额投入。
* **Pay-as-you-go（按使用付费）**：根据实际资源使用量支付费用。

---

### 3. Hybrid Cloud（混合云）

混合云把公有云和私有云连接起来共同使用。企业不必在两者之间二选一，可以根据业务、安全、成本和合规要求决定各个系统的运行位置。

| 特点                                 | 通俗解释                               | 影响                     |
| ------------------------------------ | -------------------------------------- | ------------------------ |
| 同时使用公有云和私有云               | 一部分系统放自己这里，一部分放公共云   | 灵活性最高               |
| 企业可以决定每个应用运行在哪里       | 不同业务根据需求选择最适合的环境       | 可以兼顾成本、安全和性能 |
| 私有云资源不足时，可以借用公有云资源 | 临时高峰不需要提前购买大量硬件         | 更容易应对短期流量增长   |
| 敏感服务可以保留在私有云             | 不适合上公有云的数据仍然留在企业内部   | 更容易满足安全或法律要求 |
| 普通服务可以使用公有云               | 对安全要求较低的系统可以利用公有云优势 | 降低成本并提高扩展能力   |

例如，企业可以按以下方式分配工作负载：

```text id="u0dy1n"
核心客户数据库
→ 私有云

公开网站
→ Azure 公有云

流量突然增加
→ 临时增加 Azure 资源
```

这样企业既能保留核心系统的控制权，又能利用公有云的快速扩展能力。

**关键词**

* **Hybrid Cloud（混合云）**：将公有云和私有云连接并共同使用的云环境。
* **Cloud Bursting**：私有云资源不足时，临时使用公有云资源处理额外负载。
* **Compliance（合规）**：满足法律、行业标准或组织内部规定。
* **Flexibility（灵活性）**：可以根据实际需求自由选择资源运行位置。

---

### 4. 三种云模型的比较

| 对比项         | Public Cloud               | Private Cloud          | Hybrid Cloud            |
| -------------- | -------------------------- | ---------------------- | ----------------------- |
| 谁可以使用     | 多个客户                   | 单一组织               | 公有云 + 单一组织私有云 |
| 基础设施投入   | 通常不需要提前购买大量硬件 | 通常需要购买和维护硬件 | 根据私有云规模决定      |
| 扩容速度       | 很快                       | 通常较慢               | 可以借助公有云快速扩容  |
| 控制权         | 较低                       | 最高                   | 可以按业务分别控制      |
| 运维负担       | 较低                       | 较高                   | 中等到较高              |
| 按需使用能力   | 强                         | 相对较弱               | 较强                    |
| 安全和合规控制 | 受云平台能力限制           | 可以完全自行控制       | 可以按需求选择部署位置  |
| 灵活性         | 高                         | 相对较低               | 最高                    |

三种模型的差异可以概括为：

```text id="se7ij8"
Public Cloud
便宜、灵活、扩展快
但控制权相对少

Private Cloud
控制权强
但成本和维护负担高

Hybrid Cloud
两者结合
可以按需求选择
```

---

### 5. Multicloud（多云）

Multicloud 是同时使用两个或更多公有云服务商，例如：

```text id="imk1tv"
Microsoft Azure
+
Amazon Web Services
+
Google Cloud
```

企业采用多云的原因包括平台能力差异、迁移需要、降低供应商依赖，以及不同团队各自选择了不同平台：

| 原因                   | 通俗解释                                       |
| ---------------------- | ---------------------------------------------- |
| 不同云平台各有优势     | 某个平台的 AI 更合适，另一个平台的数据库更适合 |
| 正在进行云迁移         | 原来使用一个云厂商，现在正在逐步迁移到另一个   |
| 避免完全依赖单一供应商 | 不把所有业务完全绑定在一个云平台               |
| 不同团队使用不同平台   | 不同业务部门可能选择不同云服务商               |

多云环境也增加了管理负担，因为团队需要同时维护多个平台中的资源、安全策略和配置。

**关键词**

* **Multicloud（多云）**：同时使用多个公有云服务商。
* **Cloud Provider（云服务商）**：例如 Microsoft、AWS、Google。
* **Vendor Lock-in（供应商锁定）**：系统高度依赖某个厂商，导致未来很难迁移到其他平台。

---

### 6. Azure Arc

Azure Arc 是微软提供的一组管理技术，帮助企业通过 Azure 管理不同位置和平台上的资源，范围包括：

* Azure 公有云
* 企业自己的私有云
* 混合云
* 多云环境

管理关系可以表示为：

```text id="73c4fr"
Azure
      \
本地服务器
       \
AWS ------ Azure Arc
       /
其他云
```

Azure Arc 提供统一的管理入口，让分散在不同环境中的资源能够采用较为一致的管理方式。

**关键词**

* **Azure Arc**：用于统一管理 Azure、本地、私有云和其他云资源的一组 Azure 技术。
* **Hybrid Management（混合环境管理）**：使用统一工具管理本地和云端资源。
* **Multicloud Management（多云管理）**：统一管理不同云服务商中的资源。

---

### 7. Azure VMware Solution

已经使用 VMware 构建私有云的企业迁移到 Azure 时，需要处理原有工作负载。Azure VMware Solution 允许这些工作负载直接在 Azure 中运行，让企业保留现有 VMware 技术体系，同时逐步使用 Azure 的公有云和扩展能力。

**通俗理解**

原本：

```text id="9qx4rm"
企业数据中心
↓
VMware
↓
大量虚拟机
```

想迁移到 Azure 时，不一定需要立即：

```text id="3c29ii"
全部重写
全部重新部署
全部改变架构
```

而可以：

```text id="dkfk99"
现有 VMware 工作负载
        ↓
Azure VMware Solution
        ↓
在 Azure 中继续运行
```

**关键词**

* **VMware**：常见的企业虚拟化平台。
* **Workload（工作负载）**：为了完成某项业务而运行的一组应用、服务和资源。
* **Azure VMware Solution**：允许 VMware 工作负载在 Azure 中运行的服务。
* **Migration（迁移）**：将应用、数据或工作负载从一个环境移动到另一个环境。

---

### 本节总结

云部署模型主要回答资源部署在哪里以及由谁使用。三种基本模型如下：

| 模型          | 一句话理解                           |
| ------------- | ------------------------------------ |
| Public Cloud  | **使用云厂商向大量客户开放的云平台** |
| Private Cloud | **整个云环境只服务一个组织**         |
| Hybrid Cloud  | **公有云和私有云连接起来一起使用**   |

Multicloud 则表示同时使用多个公有云厂商。三种部署模型之间的关系可以整理为：

```text id="9wpr2w"
Private Cloud
自己的专用云
      ↓
Hybrid Cloud
自己的云 + 公有云
      ↓
Public Cloud
云厂商提供的公共云
```

Multicloud 属于另一个维度：

```text id="zf4j0h"
Azure + AWS + Google Cloud + ...
```

私有云侧重控制，公有云侧重灵活和按需使用，混合云结合两者，多云则表示同时使用多个公有云平台。

## 云计算消费模型（Consumption-based Model）

云计算通常采用 Consumption-based Model（基于使用量的消费模型）：需要多少 IT 资源就使用多少，并按实际用量付费，不再需要时再释放。传统 IT 往往要提前购买服务器、网络设备和机房空间，而云计算更接近租用资源，区别可以概括为“传统 IT 先买再用，云计算按需租用”。

---

### 1. CapEx 与 OpEx

传统 IT 预算通常区分 CapEx 和 OpEx：

| 概念  | 通俗解释                         | 例子                         |
| ----- | -------------------------------- | ---------------------------- |
| CapEx | 提前花一大笔钱购买长期使用的资产 | 购买服务器、交换机、机房设备 |
| OpEx  | 随着使用过程持续产生的运营费用   | 每月支付云服务费用           |

云计算通常归入 OpEx，因为资源不是一次性买下，而是根据使用情况持续付费。传统数据中心的支出过程如下：

```text
传统数据中心：
先花钱买服务器
↓
服务器买下来以后长期使用
↓
属于 CapEx
```

云计算的支出则随资源用量变化：

```text
这个月用了 10 台虚拟机
↓
支付对应费用

下个月只需要 3 台
↓
只支付 3 台的费用
```

因此，这类费用属于 OpEx。

**关键词**

* **CapEx（Capital Expenditure，资本支出）**：提前投入资金购买服务器、网络设备、机房等长期资产。
* **OpEx（Operational Expenditure，运营支出）**：随着业务运行持续产生的费用。
* **Consumption-based Model（基于使用量的消费模型）**：根据实际使用的资源量计费。
* **Cloud Resource（云资源）**：云平台提供的虚拟机、存储、数据库等资源。

---

### 2. 基于使用量模型的优势

| 优势                                 | 通俗解释                               | 作用                   |
| ------------------------------------ | -------------------------------------- | ---------------------- |
| 不需要提前购买硬件和数据中心基础设施 | 不用先花大量资金采购服务器             | 降低初始投入           |
| 不需要提前购买可能用不上的容量       | 不必为了预测未来需求而买一堆闲置服务器 | 减少资源浪费           |
| 需求增加时可以增加资源               | 流量突然变大时，可以快速加机器         | 应对业务增长和流量高峰 |
| 需求下降时可以释放资源               | 高峰结束后，把不用的资源删掉           | 避免继续为空闲资源付费 |

这种模式的核心是让资源投入尽可能贴近真实业务需求。

---

### 3. 传统数据中心中的容量规划

传统数据中心需要提前预测未来的资源需求。例如，预计未来一年需要 20 台服务器时，可能要完成以下流程：

```text
预测需求
↓
采购服务器
↓
运输
↓
安装
↓
配置电力和网络
↓
部署应用
```

容量预测很难完全准确，过高或过低都会带来问题：

| 情况     | 结果                                     |
| -------- | ---------------------------------------- |
| 高估需求 | 买了太多服务器，大量资源长期闲置         |
| 低估需求 | 服务器不够，应用性能下降甚至无法提供服务 |

如果容量不足，企业也无法立即补充资源，还要重新采购、安装和配置硬件。

**关键词**

* **Capacity Planning（容量规划）**：提前预测未来需要多少计算、存储和网络资源。
* **Underutilized（利用不足）**：买来的资源没有得到充分使用。
* **Degraded Performance（性能下降）**：因为资源不足，系统响应变慢或处理能力下降。
* **Provisioning（预配）**：准备并配置资源，使其能够投入使用。

---

### 4. 云计算中的容量规划

云计算不必完全依赖长期预测，可以根据实际需求调整资源。例如：

```text
平时：
5 台虚拟机

促销活动开始：
流量增加
↓
增加到 20 台虚拟机

活动结束：
流量下降
↓
减少回 5 台
```

这样可以使资源容量更接近实际业务需求。

| 云中的做法         | 通俗解释                 | 作用         |
| ------------------ | ------------------------ | ------------ |
| 需求增加时添加资源 | 忙的时候多开机器         | 防止容量不足 |
| 需求下降时删除资源 | 闲的时候把多余机器关掉   | 减少浪费     |
| 按实际使用量计费   | 不需要为空闲资源持续付费 | 提高成本效率 |
| 根据流量动态调整   | 容量可以跟着业务变化     | 提高灵活性   |

---

### 5. Scale Out 与 Scale In

**Scale Out**

Scale Out 是增加更多资源或实例，例如：

```text
5 台服务器
↓
流量上涨
↓
增加到 20 台服务器
```

**Scale In**

Scale In 是在需求降低后减少资源或实例，例如：

```text
20 台服务器
↓
流量下降
↓
减少到 5 台服务器
```

两者与需求变化的关系如下：

```text
需求增加
→ Scale Out

需求下降
→ Scale In
```

**关键词**

* **Scale Out（横向扩展）**：增加更多服务器或实例。
* **Scale In（横向缩减）**：减少服务器或实例。
* **Scaling（扩缩容）**：根据业务负载增加或减少系统资源。
* **Capacity（容量）**：系统能够处理的最大工作负载。

---

### 6. Pay-as-you-go 定价

云服务商通常采用 Pay-as-you-go（按使用付费）的定价模式，也就是用了多少资源就支付多少费用。这与传统方式先购买一批服务器、之后无论是否充分使用都已经产生支出有明显区别。

| Pay-as-you-go 带来的好处 | 通俗解释                                 |
| ------------------------ | ---------------------------------------- |
| 更容易管理运营成本       | 费用更直接地跟实际资源使用情况关联       |
| 提高基础设施利用率       | 减少大量长期闲置资源                     |
| 可以根据负载调整成本     | 业务增长时多花钱，业务下降时减少支出     |
| 不必自己维护底层基础设施 | 电力、冷却、硬件、物理网络由云服务商负责 |

**关键词**

* **Pay-as-you-go（按使用付费）**：根据实际使用的云资源计费。
* **Idle Capacity（闲置容量）**：已经购买或分配，但当前没有实际使用的资源。
* **Operating Cost（运营成本）**：系统持续运行过程中产生的费用。

---

### 7. 为什么云计算能做到这种模式

云服务商维护底层的大规模基础设施，包括：

* 电力
* 冷却
* 物理服务器
* 物理网络

客户不需要自行购买这些基础设施，而是使用云服务商已经建好的资源池：

```text
云服务商
提前建设大量基础设施
        ↓
形成巨大的资源池
        ↓
客户需要资源时申请
        ↓
不用时释放
```

客户因此可以把更多精力放在业务问题和应用功能上，而不是购买、安装和维护硬件。

---

### 本节总结

基于使用量的消费模型改变了资源规划方式。传统 IT 的流程是：

```text
传统 IT：

预测未来需求
↓
提前买硬件
↓
固定容量
↓
高估 = 浪费
低估 = 性能不足
```

云计算的流程则是：

```text
云计算：

实际需求增加
↓
增加资源

实际需求下降
↓
释放资源

↓
按实际使用量付费
```

三个概念的关系如下：

| 概念                    | 一句话理解               |
| ----------------------- | ------------------------ |
| CapEx                   | **先买资产，再慢慢用**   |
| OpEx                    | **随着使用持续付费**     |
| Consumption-based Model | **用多少资源，付多少钱** |

云计算在容量规划上的主要优势，是不再要求企业准确预测未来所需的全部基础设施，而是允许资源随着实际需求扩缩。

## Azure 物理基础架构

Azure 的核心架构组件分为两类：

* **Physical Infrastructure（物理基础架构）**
* **Management Infrastructure（管理基础架构）**

这一部分讨论物理基础架构。Azure 不让用户直接管理某台物理服务器，而是通过 Datacenter、Region、Availability Zone 和 Region Pair 组织全球资源，使工作负载能够在更高层次上部署，并获得故障隔离、可靠性和韧性。

---

### 1. Datacenter（数据中心）

Azure 的物理基础从 Datacenter 开始。它与传统企业数据中心类似，包含：

* 服务器
* 机架
* 电力系统
* 冷却系统
* 网络设备

主要区别在于规模，Azure 在世界各地拥有大量数据中心。用户通常不会选择某个具体 Datacenter，而是通过更高层次的 Region 和 Availability Zone 部署资源。

| 设计概念                                                | 通俗解释                                 | 作用                            |
| ------------------------------------------------------- | ---------------------------------------- | ------------------------------- |
| Datacenter 是 Azure 最底层的物理设施                    | 真正的服务器、网络、电力、冷却都在这里   | 为 Azure 云服务提供实际硬件基础 |
| 用户通常不直接操作具体 Datacenter                       | 你不会选择“把 VM 放到第几栋机房”         | Azure 可以自行管理底层资源      |
| Datacenter 会被进一步组织成 Region 和 Availability Zone | 把大量物理机房抽象成更容易使用的逻辑结构 | 提供更好的可靠性和故障隔离      |

**关键词**

* **Datacenter（数据中心）**：容纳服务器、网络、电力和冷却设施的物理场所。
* **Rack（机架）**：用于安装服务器和网络设备的物理机柜。
* **Physical Infrastructure（物理基础架构）**：真正的机房、服务器、电力、网络等硬件设施。

---

### 2. Region（区域）

Azure Region 是包含一个或多个邻近数据中心的地理区域，这些数据中心通过低延迟网络连接。创建 Azure 资源时，通常需要从以下这类 Region 中选择部署位置：

```text
Japan East
West Europe
East US
Southeast Asia
```

| 设计概念                                  | 通俗解释                                            | 作用                                 |
| ----------------------------------------- | --------------------------------------------------- | ------------------------------------ |
| 一个 Region 包含一个或多个邻近 Datacenter | Region 不是一个机房，而是一组地理位置接近的数据中心 | 把底层数据中心组织成可管理的部署区域 |
| Region 内部使用低延迟网络连接             | 同一区域内的数据中心之间通信速度较快                | 适合组成一个完整的区域级云环境       |
| 创建 Azure 资源时通常需要选择 Region      | 决定 VM、数据库等资源主要部署在哪里                 | 影响延迟、合规、服务可用性和成本     |
| Azure 会在 Region 内管理资源分配和负载    | 用户不需要自己指定某台实体服务器                    | Azure 自动管理底层资源               |

Region 可以理解为 Azure 在某个地理范围内建立的一整套云基础设施。例如，在日本部署服务时可以选择 Japan East，使服务更接近日本用户。

---

### 3. Region 并不是所有服务都一样

并非所有 Azure 服务和功能都在每个 Region 中提供，常见差异包括：

* 某些 VM Size 只在部分 Region 可用
* 某些 Storage 类型只在部分 Region 可用
* 某些特殊服务只部署在指定 Region

因此，选择部署位置时既要考虑与用户的距离，也要确认目标 Region 是否提供所需服务。Microsoft Entra ID、Azure Traffic Manager 和 Azure DNS 等 Global Service 则不要求选择具体 Region：

* Microsoft Entra ID
* Azure Traffic Manager
* Azure DNS

**关键词**

* **Region（区域）**：由一个或多个邻近数据中心组成的 Azure 地理部署范围。
* **Low-latency Network（低延迟网络）**：具有较低通信延迟的高速网络。
* **Global Service（全球服务）**：不要求用户选择特定 Azure Region 的服务。
* **VM Size**：Azure VM 不同的 CPU、内存和硬件规格组合。

---

### 4. Availability Zone（可用区）

Availability Zone 是同一个 Azure Region 内彼此物理分离的数据中心区域，每个 Zone 都有独立的：

* 电力
* 冷却
* 网络

一个 Zone 出现故障时，其他 Zone 仍可继续运行；各 Zone 之间则通过高速私有光纤网络连接，以支持跨 Zone 通信和复制。

| 设计概念                                | 通俗解释                                             | 作用                       |
| --------------------------------------- | ---------------------------------------------------- | -------------------------- |
| Availability Zone 在物理上彼此分离      | 虽然都属于同一个 Region，但不是共用同一个机房环境    | 减少单一机房故障造成的影响 |
| 每个 Zone 有独立电力、冷却和网络        | 一个 Zone 的供电或网络故障不会必然拖垮其他 Zone      | 提供故障隔离               |
| Zone 之间通过高速私有网络连接           | 不同 Zone 仍然可以快速通信                           | 支持跨 Zone 冗余和复制     |
| 一个 Zone 可以包含一个或多个 Datacenter | Availability Zone 是比单一机房更高一层的故障隔离单位 | 提供更稳定的可用性边界     |

假设一个 Region 有三个 Availability Zone：

```text
Azure Region
├── Zone 1
├── Zone 2
└── Zone 3
```

如果 Zone 1 因为电力问题完全故障：

```text
Zone 1 ✕
Zone 2 ✓
Zone 3 ✓
```

只要服务跨多个 Zone 部署，Zone 1 的电力故障就不会必然中断整个服务。因此，Availability Zone 主要解决同一个 Region 内的机房级故障。

---

### 5. Availability Zone 是故障隔离边界

Azure 把 Availability Zone 设计成 Isolation Boundary（隔离边界），目标是把故障限制在单个 Zone 内，避免影响其他 Zone。这与前文的 Fault Isolation 思路一致：

```text
Zone 1
电力故障
↓
Zone 1 服务停止

Zone 2 / Zone 3
独立供电
↓
继续运行
```

对于支持 Availability Zone 的 Region，Azure 至少提供三个独立 Zone。

不过，并非所有 Azure Region 都支持 Availability Zone。

**关键词**

* **Availability Zone（可用区）**：Region 内物理隔离的基础设施区域。
* **Isolation Boundary（隔离边界）**：一个故障尽量被限制在该范围内，不继续向外扩散。
* **Fault Isolation（故障隔离）**：阻止局部故障影响其他资源的设计方式。

---

### 6. 如何利用 Availability Zone 提高可靠性

传统本地数据中心通常要购买两套或多套硬件才能实现冗余，而 Azure 可以把资源直接部署到不同 Availability Zone，例如：

```text
Zone 1
VM A

Zone 2
VM B

Zone 3
VM C
```

某个 Zone 出现故障后，其他 Zone 中的资源仍然存在。可以跨 Zone 部署的资源包括：

* VM
* Storage
* Database
* 其他支持 Availability Zone 的 Azure 服务

跨 Zone 冗余也会增加成本，例如：

* 创建更多资源副本
* 跨 Zone 传输数据
* 保存更多数据副本

因此，设计时仍需权衡可靠性与成本。

---

### 7. Availability Zone 服务的三种类型

支持 Availability Zone 的 Azure 服务大致分为三类：

| 类型                   | 通俗解释                        | 例子                                 |
| ---------------------- | ------------------------------- | ------------------------------------ |
| Zonal Service          | 你自己指定资源放在哪个 Zone     | VM、Managed Disk、IP Address         |
| Zone-redundant Service | Azure 自动在多个 Zone 之间复制  | Zone-redundant Storage、SQL Database |
| Non-regional Service   | 服务本身不依赖某一个单独 Region | 一些全球性 Azure 服务                |

**Zonal Service**

使用 Zonal Service 时，用户明确指定资源所在的 Zone：

```text
VM A → Zone 1
VM B → Zone 2
```

跨 Zone 冗余需要由用户设计。

**Zone-redundant Service**

使用 Zone-redundant Service 时，用户只需创建服务，Azure 平台会在多个 Zone 中部署副本：

```text
Zone 1
Zone 2
Zone 3
```

多 Zone 复制由平台自动完成。

**Non-regional Service**

Non-regional Service 不绑定单个 Region，因此可以抵御：

* Zone 级故障
* Region 级故障

**关键词**

* **Zonal Service**：绑定到某一个特定 Availability Zone 的资源。
* **Zone-redundant Service**：Azure 自动将服务复制到多个 Zone。
* **Non-regional Service**：不依赖单一区域的服务。
* **Managed Disk**：Azure 管理的 VM 磁盘。
* **Zone-redundant Storage，ZRS**：自动在同一个 Region 的多个 Availability Zone 之间复制数据的存储方式。

---

### 8. 为什么有 Availability Zone 还需要 Region Pair

Availability Zone 可以应对单个 Zone 故障，但大规模自然灾害、区域级电力或网络中断、社会事件以及整个 Region 的基础设施问题，可能同时影响同一区域内的多个 Zone：

* 大规模自然灾害
* 区域级电力中断
* 大规模网络故障
* 社会事件
* 整个 Region 的基础设施问题

为了应对这类 Region 级故障，Azure 提供了 Region Pair（区域对）。

---

### 9. Region Pair（区域对）

大多数 Azure Region 会与同一 Geography 中的另一个 Region 配对。两个 Region 通常至少相距约 300 英里，以降低同一场区域性灾难同时影响两边的可能性，例如：

```text
West US ↔ East US

Southeast Asia ↔ East Asia
```

| 设计概念                           | 通俗解释                                 | 作用                         |
| ---------------------------------- | ---------------------------------------- | ---------------------------- |
| 两个 Region 组成 Region Pair       | 一个区域还有另一个远距离区域作为恢复选择 | 提高 Region 级灾难的恢复能力 |
| 两个 Region 距离较远               | 避免同一次区域灾难同时破坏两个 Region    | 降低相关性故障风险           |
| 可以跨 Region 复制资源或数据       | 一个 Region 故障后可以使用另一个 Region  | 提供更高级别的灾难恢复       |
| Region Pair 通常位于同一 Geography | 数据通常不会跨出所要求的地理范围         | 有利于数据驻留和合规         |

Availability Zone 类似一个城市里的多个独立机房，Region Pair 则相当于在远处的另一个城市准备一套恢复环境。

---

### 10. Region Pair 并不等于自动灾备

Region Pair 只提供跨区域恢复的基础条件，并不表示 Azure 会自动复制所有数据和服务。事实上，并非所有服务都会：

* 自动跨 Region 复制
* 自动 Failover
* 自动 Failback

很多情况下，客户仍需自行配置：

* 数据复制
* 备用 Region
* Failover
* Disaster Recovery

是否进行跨 Region 复制和恢复，最终取决于服务本身的能力和客户配置。

**关键词**

* **Region Pair（区域对）**：两个相距较远、用于增强区域级灾难恢复能力的 Azure Region。
* **Cross-region Replication（跨区域复制）**：把数据或资源复制到另一个 Region。
* **Failover（故障切换）**：主 Region 故障后切换到备用 Region。
* **Failback（故障回切）**：主 Region 恢复后再切回。
* **Disaster Recovery，DR（灾难恢复）**：发生大规模严重故障后恢复业务的整体能力。

---

### 11. Region Pair 的额外优势

除跨区域复制外，Region Pair 还有以下作用：

| 优势                                                  | 通俗解释                                     | 作用                       |
| ----------------------------------------------------- | -------------------------------------------- | -------------------------- |
| 大规模 Azure 故障时，会优先恢复每对 Region 中至少一个 | 微软会尽量保证一对 Region 不会长期一起不可用 | 提高恢复概率               |
| Azure 计划更新通常不会同时更新两个配对 Region         | 一个更新时，另一个暂时保持不变               | 降低更新导致同时故障的风险 |
| 数据通常保持在同一个 Geography 内                     | 数据不会随意跨出某个国家或地理范围           | 满足数据驻留和合规需求     |

---

### 12. Region Pair 的特殊情况

大多数 Region Pair 是双向的：

```text
Region A ↔ Region B
```

这表示 A 和 B 互为备份选择，但并非所有 Region 都采用这种方式。Brazil South 就是一个特殊案例：

```text
Brazil South
→ South Central US
```

这种配对并不完全对称，还有一些 Region 没有传统 Region Pair，例如：

* Italy North
* Poland Central
* Israel Central

这些 Region 更多依赖以下机制实现韧性：

* Availability Zone
* Geo-redundant Storage


**关键词**

* **Bidirectional Pairing（双向配对）**：两个 Region 互相作为配对区域。
* **One-direction Pairing（单向配对）**：Region A 使用 Region B 作为配对，但反过来并不成立。
* **Geo-redundant Storage（地理冗余存储）**：把数据复制到较远的另一个地理区域，以应对 Region 级故障。

---

### 13. Geography

Geography 是比 Region 更大的地理边界，例如：

```text
United States
Europe
Asia
```

一个 Geography 可以包含多个 Region，整体层级如下：

```text
Geography
    ↓
Region
    ↓
Availability Zone
    ↓
Datacenter
```

Geography 的范围最大，Datacenter 则是最具体的物理层级。

**关键词**

* **Geography（地理区域）**：Azure 用来组织多个 Region 的更大地理范围，通常与数据驻留和合规要求相关。
* **Data Residency（数据驻留）**：规定数据应存储在哪个国家或地理范围内。

---

### 14. Sovereign Region（主权区域）

除普通 Azure Region 外，还有 Sovereign Region（主权区域）。它们与 Azure 的全球基础设施在物理和逻辑上隔离，主要用于满足：

* 政府要求
* 法律要求
* 合规要求
* 数据主权要求

| 类型                  | 通俗解释                                          |
| --------------------- | ------------------------------------------------- |
| US Government Regions | 专门为美国政府机构和合作伙伴提供的隔离 Azure 环境 |
| China Regions         | 中国地区独立运营的 Azure 环境                     |

**美国政府区域**

美国政府区域包括：

* US DoD Central
* US Gov Virginia
* US Gov Arizona

这些环境具有以下特点：

* 与普通 Azure 网络隔离
* 面向美国政府机构及合作伙伴
* 由经过审查的美国人员运营
* 具备额外合规认证

**中国区域**

中国区域包括：

* China East
* China North

中国 Azure 由 Microsoft 与 21Vianet 合作提供，Microsoft 不直接维护这些数据中心。

**关键词**

* **Sovereign Region（主权区域）**：与普通全球 Azure 环境隔离、用于满足特殊法律和合规要求的云区域。
* **Logical Isolation（逻辑隔离）**：虽然都是 Azure 技术体系，但网络、账号或管理体系彼此独立。
* **Compliance Certification（合规认证）**：证明云环境符合特定政府、行业或法律标准的认证。
* **21Vianet（世纪互联）**：在中国运营相关 Azure 云服务的合作伙伴。

---

### 总结

Azure 的物理架构层级如下：

```text
Geography
    ↓
Region
    ↓
Availability Zone
    ↓
Datacenter
    ↓
Physical Servers
```

每个层级解决的问题不同：

| 层级              | 主要解决什么问题                     |
| ----------------- | ------------------------------------ |
| Datacenter        | 真正在哪里运行服务器                 |
| Availability Zone | 一个机房级故障时怎么办               |
| Region            | 资源主要部署在哪个地理区域           |
| Region Pair       | 整个 Region 出现严重故障时怎么办     |
| Geography         | 数据和资源属于哪个大的地理、合规范围 |
| Sovereign Region  | 特殊政府、法律和数据主权要求         |

其中最容易混淆的是 Availability Zone 与 Region Pair：

```text
Availability Zone
同一个 Region 内的故障隔离
```

相比之下：

```text
Region Pair
不同 Region 之间的灾难恢复
```

简而言之，Zone 处理机房级故障，Region Pair 处理区域级灾难。Azure 的物理可靠性设计通过以下层级逐步扩大故障隔离范围：

```text
一台服务器坏了
↓
Datacenter 内处理

一个机房 / Zone 坏了
↓
其他 Availability Zone 继续运行

整个 Region 坏了
↓
另一个 Region / Region Pair 提供恢复能力
```

Azure 通过 Datacenter → Availability Zone → Region → Region Pair 的多层结构，把故障隔离和冗余能力从单个数据中心扩展到整个地理区域。


## Azure 管理基础架构

Azure 的管理基础架构主要包括：

* **Resources（资源）**
* **Resource Groups（资源组）**
* **Subscriptions（订阅）**
* **Management Groups（管理组）**
* **Accounts / Microsoft Entra Tenant（账户 / 租户）**

这些层级共同决定资源如何组织、权限如何控制以及费用如何管理，完整关系如下：

```text id="mgmt01"
Tenant Root Group
    ↓
Management Groups
    ↓
Subscriptions
    ↓
Resource Groups
    ↓
Resources
```

---

### 1. Azure Resource（资源）

Resource 是 Azure 中最基本的管理对象。在 Azure 中创建、预配或部署的服务实例通常都属于 Resource，例如：

* Virtual Machine
* Virtual Network
* Database
* Storage Account
* Azure AI Service

| 概念                        | 通俗解释                      | 作用                       |
| ------------------------- | ------------------------- | ------------------------ |
| Resource 是 Azure 最基本的构建单元 | 你实际创建出来并使用的 Azure 服务，就是资源 | 所有部署、权限、监控和计费最终都会落到具体资源上 |

**关键词**

* **Resource（资源）**：Azure 中实际创建出来的服务实例。
* **Provision（预配）**：创建并准备资源，使其能够使用。
* **Deploy（部署）**：把资源、应用或配置真正放到环境中运行。

---

### 2. Resource Group（资源组）

Resource Group 是一组 Azure Resources 的逻辑集合，每个 Resource 必须且只能同时属于一个 Resource Group。例如：

```text id="mgmt02"
Resource Group: Web-App-Prod

├── VM
├── Virtual Network
├── SQL Database
└── Storage Account
```

资源组不是物理位置，而是组织相关资源的逻辑容器。

| 设计规则                                     | 通俗解释                   | 作用            |
| ---------------------------------------- | ---------------------- | ------------- |
| 每个 Resource 必须属于一个 Resource Group        | Azure 不允许资源完全“散着放”     | 让所有资源都有明确管理归属 |
| 一个 Resource 同一时间只能属于一个 Resource Group    | 一台 VM 不能同时放进两个资源组      | 避免管理边界混乱      |
| 某些 Resource 可以在 Resource Group 之间移动      | 如果分组方式发生变化，可以把部分资源重新归类 | 提高组织灵活性       |
| Resource Group 不能嵌套                      | 不能在一个资源组里面再建另一个资源组     | 保持层级简单        |
| Resource Group 创建后不能重命名                  | 名字要在一开始就规划好            | 避免后期命名混乱      |
| 对 Resource Group 执行某些操作，会影响里面所有 Resource | 管理动作可以批量向下作用           | 方便统一管理        |

**为什么 Resource Group 很重要**

Resource Group 不只是用于分类的“文件夹”，在其范围内执行的删除或权限配置等操作可能作用于组内资源。

**删除 Resource Group**

```text id="mgmt03"
Delete Resource Group
        ↓
里面所有 Resources 一起删除
```

所以，如果你建立一个临时开发环境：

```text id="mgmt04"
Dev-Test Resource Group

├── VM
├── Database
├── Storage
└── Network
```

测试结束后可以直接删除整个 Resource Group，不必逐个清理资源。

**权限控制**

如果给某个用户授予 Resource Group 的访问权限：

```text id="mgmt05"
User
↓
获得 Resource Group 权限
↓
可以访问组内相应 Resources
```

因此，Resource Group 也是常用的权限管理范围。

**如何划分 Resource Group**

Azure 没有规定资源组的唯一划分方式，组织可以根据实际需求按项目划分：

```text id="mgmt06"
Project A Resource Group
Project B Resource Group
Project C Resource Group
```

也可以按环境划分：

```text id="mgmt07"
Dev Resource Group
Test Resource Group
Prod Resource Group
```

另一种方式是把生命周期相同的应用资源放在一起。划分时应优先考虑生命周期、权限和管理方式是否相近，例如临时测试环境中的 VM、数据库和网络通常一起创建和删除，适合放在同一个 Resource Group。

**关键词**

* **Resource Group（资源组）**：用于组织和统一管理 Azure Resources 的逻辑容器。
* **Lifecycle（生命周期）**：资源从创建、运行到删除的整个过程。
* **Naming Convention（命名规范）**：统一规定资源和资源组如何命名。
* **Access Control（访问控制）**：规定谁能够访问和操作哪些资源。

---

### 3. Azure Subscription（订阅）

Subscription 是 Azure 的资源组织、访问控制和费用管理边界，Resource Group 位于 Subscription 之下：

```text id="mgmt08"
Subscription
    ↓
Resource Groups
    ↓
Resources
```

一个 Azure Account 可以拥有多个 Subscription，但至少需要一个 Subscription 才能使用 Azure 服务。

| Subscription 的作用 | 通俗解释                               |
| ---------------- | ---------------------------------- |
| Management Unit  | 用来组织一批 Resource Groups 和 Resources |
| Billing Unit     | Azure 可以按照不同 Subscription 分别统计费用   |
| Access Boundary  | 不同 Subscription 可以配置不同权限和访问策略      |
| Scale Boundary   | 可以通过多个 Subscription 扩大和分隔资源管理范围    |

**计费边界**

Subscription 可以作为独立的计费边界。例如：

```text id="mgmt09"
Azure Account
├── Dev Subscription
├── Test Subscription
└── Production Subscription
```

Azure 可以分别产生：

```text id="mgmt10"
Dev → 一份费用报告
Test → 一份费用报告
Production → 一份费用报告
```

分开统计后，组织可以清楚地看到各项目、团队或环境产生的费用。

| 做法                        | 通俗解释            | 作用      |
| ------------------------- | --------------- | ------- |
| 为不同业务创建不同 Subscription    | 把费用拆开统计         | 方便成本追踪  |
| 为生产和开发环境使用不同 Subscription | 生产成本不会和测试成本混在一起 | 提高财务可见性 |
| 为不同团队创建 Subscription      | 每个团队单独计算云资源成本   | 方便预算管理  |

**关键词**

* **Billing Boundary（计费边界）**：费用统计和账单划分的范围。
* **Billing Report（费用报告）**：记录某个 Subscription 使用了多少 Azure 服务以及产生多少费用。
* **Cost Tracking（成本追踪）**：分析云费用来自哪些项目、团队或资源。

**访问控制边界**

Subscription 同时也是权限控制边界，不同环境可以采用不同的权限配置：

```text id="mgmt11"
Development Subscription
开发人员拥有较高权限

Production Subscription
只有少数运维人员能够修改
```

这种隔离可以降低开发人员测试代码时误操作生产资源的风险。各 Subscription 还可以分别设置 Access Policy、Budget / Cost Alert 和 Resource Permission。只有 Free Trial、Visual Studio 等带额度的订阅才可能具有 Spending Limit，按使用付费的订阅通常通过预算和告警监控成本。

| 做法                           | 通俗解释          | 作用      |
| ---------------------------- | ------------- | ------- |
| Dev 和 Prod 使用不同 Subscription | 把开发环境和生产环境隔离  | 减少误操作风险 |
| 不同 Subscription 配置不同权限       | 不同团队只能操作自己的资源 | 加强安全性   |
| 不同 Subscription 设置预算和成本告警     | 分别监控各环境的支出    | 控制成本风险  |

**关键词**

* **Access Control Boundary（访问控制边界）**：权限规则可以独立配置的一层管理范围。
* **Budget / Cost Alert（预算 / 成本告警）**：跟踪费用并在达到阈值时通知相关人员，但不会自动停止资源。
* **Access Policy（访问策略）**：规定谁可以执行哪些操作。

**为什么创建多个 Subscription**

随着 Azure 环境扩大，单个 Subscription 往往难以同时满足环境隔离、团队授权和成本核算需求，常见拆分方式有三类。

**按环境拆分**

```text id="mgmt12"
Sandbox
Development
Test
Production
```

这样可以隔离生命周期不同的环境。

**按团队或工作负载拆分**

```text id="mgmt13"
Team A Subscription
Team B Subscription
Project C Subscription
```

这样更容易分别管理权限和费用。

**按计费需求拆分**

按计费需求拆分时，可以采用以下结构：

```text id="mgmt14"
Production Subscription
Development & Test Subscription
```

这样财务部门可以清楚区分正式业务成本与开发测试成本。

---

### 4. Azure Management Group（管理组）

少量 Subscription 可以逐个管理，但大型企业可能拥有：

```text id="mgmt15"
几十个
几百个
甚至几千个 Subscription
```

逐个配置这些 Subscription 的权限和策略会产生大量重复工作，因此 Azure 在 Subscription 之上提供了 Management Group：

```text id="mgmt16"
Management Group
        ↓
Subscriptions
        ↓
Resource Groups
        ↓
Resources
```

Management Group 用于统一管理多个 Subscription。

**策略继承**

Management Group 支持 Policy 和 Access 向下继承。例如：

```text id="mgmt17"
Production Management Group

Policy:
VM 只能部署到 West US
        ↓
Subscription A
Subscription B
Subscription C
        ↓
所有 Resource Groups
        ↓
所有 Resources
```

下层所有 Subscription 都会受到该规则约束，不需要逐个重复配置。

| Management Group 能做什么        | 通俗解释                            | 作用         |
| ---------------------------- | ------------------------------- | ---------- |
| 对多个 Subscription 设置统一 Policy | 一条规则管很多订阅                       | 提高治理效率     |
| 统一配置 Access                  | 给用户一次授权，就可以作用到下面多个 Subscription | 减少重复权限配置   |
| 建立多层组织结构                     | 可以按照部门、区域、业务等组织 Subscription    | 模拟真实企业组织结构 |
| 向下继承配置                       | 子层级自动获得上层规则                     | 保持管理一致性    |

**Policy 继承示例**

假设公司要求 Production 环境的 VM 只能运行在 West US，可以按以下方式配置：

```text id="mgmt18"
Production Management Group

Policy:
Allowed Region = West US

├── Production Subscription A
├── Production Subscription B
└── Production Subscription C
```

在此结构中，下层 VM 都受到同一策略约束：

```text id="mgmt19"
所有下面的 VM
↓
只能部署到 West US
```

继承的上层治理策略不能由 Subscription Owner 直接绕过，因此企业可以把统一规则应用到大量 Subscription。

**Azure RBAC 与 Management Group**

Management Group 也能统一分配权限。假设某个管理员需要读取多个 Subscription，没有 Management Group 时必须逐个配置：

```text id="mgmt20"
Subscription A → 配一次权限
Subscription B → 再配一次
Subscription C → 再配一次
Subscription D → 再配一次
```

使用 Management Group 后：

```text id="mgmt21"
Management Group
↓
配置一次 Azure RBAC
↓
下面所有 Subscription 自动继承
```

权限还可以继续向下继承：

```text id="mgmt22"
Management Group
    ↓
Sub-management Group
    ↓
Subscription
    ↓
Resource Group
    ↓
Resource
```

**关键词**

* **Azure RBAC（Role-Based Access Control）**：基于角色的访问控制，用角色决定用户能够对 Azure 资源执行什么操作。
* **Role Assignment（角色分配）**：把某个 Azure Role 分配给某个用户、组或身份。
* **Inheritance（继承）**：下层资源自动获得上层定义的权限或策略。
* **Governance（治理）**：通过规则、权限和策略统一管理云资源。
* **Policy（策略）**：用于限制或规范 Azure 资源配置的规则。

**Management Group 嵌套**

Resource Group 不能嵌套，Management Group 则可以形成多层结构。例如：

```text id="mgmt23"
Tenant Root Group
│
├── Production
│   ├── Europe
│   │   ├── Subscription A
│   │   └── Subscription B
│   │
│   └── Asia
│       ├── Subscription C
│       └── Subscription D
│
└── Development
    ├── Subscription E
    └── Subscription F
```

企业可以按照部门、国家或地区、开发环境、项目和业务类型建立管理层级。Management Group 最多可以嵌套 6 层，这一限制不计算：

* Tenant Root Group
* Subscription 层

**Management Group 的限制**

Management Group 还受以下数量和层级规则限制：

| 规则                                           | 含义                                            |
| -------------------------------------------- | --------------------------------------------- |
| 一个 Directory 最多支持 10,000 个 Management Groups | Azure 对管理组数量有上限                               |
| Management Group 可以嵌套最多 6 层                  | 可以建立较复杂的组织层级                                  |
| 每个 Management Group 只能有一个 Parent             | 一个管理组不能同时属于两个上级                               |
| 每个 Subscription 只能有一个 Parent                 | 一个 Subscription 同时只能处于一个 Management Group 分支中 |

这与 Resource Group 的组织原则相似，每个对象在层级中都有明确的父级。

---

### 5. Tenant Root Group

每个 Microsoft Entra Tenant 都有一个 Tenant Root Group，它是 Management Group 层级的根节点，所有 Management Groups 和 Subscriptions 最终都位于其下。结构如下：

```text id="mgmt24"
Tenant Root Group
        ↓
Management Groups
        ↓
Subscriptions
        ↓
Resource Groups
        ↓
Resources
```

在 Tenant Root Group 上应用的 Policy 或角色分配会沿层级继承，因此可能影响整个 Tenant 下的 Azure 环境。

**关键词**

* **Microsoft Entra Tenant（Entra 租户）**：一个组织在 Microsoft Entra ID 中的独立身份和目录边界。
* **Tenant Root Group**：Management Group 层级最顶层的根管理组。
* **Directory（目录）**：保存组织用户、组、身份等信息的身份管理环境。

---

### 关键词总览

* **Azure Resource**：Azure 中实际创建和使用的服务实例。
* **Resource Group**：把相关 Resources 放在一起管理的逻辑容器。
* **Subscription**：Azure 中用于资源组织、权限控制和费用管理的边界。
* **Management Group**：用于统一管理多个 Subscription 的上层管理结构。
* **Tenant Root Group**：整个 Management Group 层级的根节点。
* **Microsoft Entra Tenant**：组织在 Microsoft Entra ID 中的独立身份目录。
* **Billing Boundary**：费用独立统计的管理边界。
* **Access Control Boundary**：权限可以独立配置的管理边界。
* **Azure RBAC**：基于角色控制用户能够访问和操作哪些 Azure 资源。
* **Azure Policy**：用于规定 Azure Resource 必须满足哪些配置和合规要求。
* **Inheritance（继承）**：上层的 Policy 或 Access 设置自动作用到下层。

---

### 总结

Azure 管理基础架构的核心是以下层级：

```text id="mgmt25"
Tenant Root Group
        ↓
Management Group
        ↓
Subscription
        ↓
Resource Group
        ↓
Resource
```

可以用公司的组织结构作类比：

| Azure 概念          | 类比             |
| ----------------- | -------------- |
| Tenant Root Group | 整个公司           |
| Management Group  | 事业部 / 部门       |
| Subscription      | 某个项目或独立预算单位    |
| Resource Group    | 项目中的某一组相关资源    |
| Resource          | 真正的 VM、数据库、网络等 |

各层承担不同职责：

| 层级                | 核心作用                |
| ----------------- | ------------------- |
| Resource          | 真正提供功能              |
| Resource Group    | 管理一组相关资源            |
| Subscription      | 隔离权限、费用和环境          |
| Management Group  | 统一管理大量 Subscription |
| Tenant Root Group | 对整个组织进行最高层治理        |

Policy 和 Access 的继承关系如下：

```text id="mgmt26"
上层 Policy / Access
        ↓
Management Group
        ↓
Subscription
        ↓
Resource Group
        ↓
Resource
```

Resource 是实际服务，Resource Group 管理一组资源，Subscription 负责资源组织、权限和费用边界，Management Group 统一管理多个 Subscription，Tenant Root Group 则位于整个 Azure 管理层级的顶层。

## Azure Monitor

### Azure Monitor 中的 SLI

SLI（Service Level Indicator，服务级别指标）用于衡量服务的实际可靠性或性能。Azure Monitor 会把实际观测到的服务表现，与预先设定的目标进行比较，从而判断服务是否达到预期。一个完整的 SLI 不只是一个指标，而是由服务范围、SLI 类型、评估方式、信号设计、SLO 目标和统计周期等共同组成。

**1. SLI 的基本组成**

| 组成部分          | 通俗解释                                       | 作用                       |
| ----------------- | ---------------------------------------------- | -------------------------- |
| Service Group     | 这个 SLI 到底是在衡量哪个应用或工作负载        | 明确测量范围               |
| SLI Type          | 你到底想测“能不能用”，还是“够不够快”           | 决定可靠性问题的类型       |
| Evaluation Method | 按每一次请求统计，还是按一段段时间窗口统计     | 决定 SLI 的计算方式        |
| Signal Design     | 用哪些指标、过滤条件、聚合方式和公式来判断好坏 | 定义什么算成功、什么算失败 |
| Baseline Target   | 实际指标需要达到的目标值，也就是 SLO           | 判断服务是否达标           |
| Compliance Period | 在多长时间范围内判断是否达标                   | 明确统计周期               |

*关键词*

* **SLI**：实际测量出来的服务表现。
* **SLO**：SLI 应该达到的目标。
* **Compliance Period**：判断 SLO 是否达标的统计时间范围，例如 7 天、30 天。
* **Signal**：用于计算 SLI 的原始监控数据和条件。

---

**2. SLI 的两种主要类型**

Azure Monitor 主要支持 Availability 和 Latency 两类 SLI：

| 类型         | 通俗解释               | 例子                       |
| ------------ | ---------------------- | -------------------------- |
| Availability | 服务到底有没有正常工作 | 99.99% 的读写请求成功      |
| Latency      | 服务响应得够不够快     | 95% 的请求在 300 ms 内完成 |

*关键词*

* **Availability（可用性）**：服务是否成功完成用户请求。
* **Latency（延迟）**：从请求发出到得到响应所需要的时间。

Availability 衡量请求是否成功，Latency 衡量响应是否足够快。

---

**3. 两种评估方式**

Azure Monitor 可以按 Request-based 或 Window-based 两种方式计算 SLI：

| 评估方式      | 通俗解释                                     | 适合场景                                     |
| ------------- | -------------------------------------------- | -------------------------------------------- |
| Request-based | 每个请求都算一次，然后看成功请求占总请求多少 | 最适合衡量接口请求成功率，是最常见方式       |
| Window-based  | 把时间切成一段一段，每一段判断“好还是坏”     | 适合不希望短时间抖动对整体结果影响太大的场景 |

**Request-based**

Request-based SLI 的核心公式是：

```text
SLI = Good Requests / Total Requests
```

以下示例中，成功请求数为 9900，总请求数为 10000：

```text
成功请求：9900
总请求：10000

SLI = 9900 / 10000 = 99%
```

其中，Good Signal 是分子，表示符合成功条件的请求；Total Signal 是分母，表示所有参与统计的请求。例如：

```text
Good Signal：
HTTP 状态码 = 200 的请求

Total Signal：
所有 HTTP 请求
```

相应的 Availability SLI 为：

```text
Availability SLI
= HTTP 200 请求数 / 总请求数
```

**Window-based**

Window-based 不直接统计成功请求占比，而是先把时间划分为多个窗口，例如每 5 分钟一个窗口：

```text
每 5 分钟作为一个窗口
```

然后逐个判断窗口是否合格：

```text
错误率 < 1%
→ Good Window

错误率 >= 1%
→ Bad Window
```

最终按合格窗口占比计算 SLI：

```text
SLI = Good Windows / Total Windows
```

这种方法能降低短暂流量尖峰对整体 SLI 的影响。

*关键词*

* **Good Signal**：满足成功条件的数据。
* **Total Signal**：参与统计的全部数据。
* **Request-based**：以请求为基本统计单位。
* **Window-based**：以时间窗口为基本统计单位。
* **Threshold（阈值）**：用于判断结果是否合格的界限值。

---

**4. Signal 如何定义**

真正创建 SLI 时，需要指定 Azure Monitor 应该使用哪些 Metrics，并通过过滤、聚合和公式定义成功条件。

| 方法                 | 通俗解释                   | 例子                           |
| -------------------- | -------------------------- | ------------------------------ |
| Metric               | 选择真正要统计的数据       | 请求数、错误数、响应时间       |
| Filter               | 只保留符合条件的数据       | 只统计 HTTP 200                |
| Temporal Aggregation | 把一段时间内的数据进行汇总 | Average、Maximum、Count        |
| Spatial Aggregation  | 把多个时间序列进一步合并   | 把多个实例的数据汇总成服务整体 |
| Formula              | 用多个指标计算出新信号     | 成功请求数 ÷ 总请求数          |

*关键词*

* **Metric（指标）**：系统持续产生的数值，例如请求数、CPU、延迟。
* **Filter（过滤）**：从所有数据中筛选出需要的数据。
* **Temporal Aggregation（时间聚合）**：对一段时间内的数据进行平均、求最大值或计数。
* **Spatial Aggregation（空间聚合）**：把来自多个实例、区域或时间序列的数据合并。
* **Formula（公式）**：通过一个或多个指标计算出最终信号。

---

**5. SLI 与 SLO 的关系**

SLI 是实际测量值，Baseline Target 是 SLI 应达到的目标，也就是 SLO。例如：

```text
SLI：
过去 30 天请求成功率 = 99.92%

SLO：
请求成功率 >= 99.9%
```

此时实际值高于目标：

```text
99.92% > 99.9%
→ 达到 SLO
```

如果实际值低于目标：

```text
SLI = 99.7%
SLO = 99.9%

→ 未达到 SLO
```

可以把 SLI 理解为实际成绩，把 SLO 理解为目标分数。

---

**6. Error Budget**

Azure Monitor 根据 SLO 计算 Error Budget，公式为：

```text
Error Budget = 100% - SLO
```

SLO 为 99.9% 时：

```text
SLO = 99.9%

Error Budget
= 100% - 99.9%
= 0.1%
```

这表示服务在当前统计周期内最多可以承受 0.1% 的不可靠性。

| 概念         | 通俗解释                                |
| ------------ | --------------------------------------- |
| SLO          | 你要求系统达到的可靠性                  |
| Error Budget | 在不违反 SLO 的前提下，还允许出多少问题 |

```text
SLO：99.9%
允许失败：0.1%
```

当 SLO 为 99.9% 时，剩余的 0.1% 就是可以被故障、发布风险或其他异常消耗的预算。

---

**7. Burn Rate**

Burn Rate 表示 Error Budget 的消耗速度。Azure Monitor 不只关心预算还剩多少，也会判断当前消耗速度是否会使预算很快耗尽。例如，初始 Error Budget 为 0.1%：

```text
Error Budget = 0.1%
```

如果统计刚开始不久就出现以下情况：

```text
已经消耗 0.08%
```

即使服务暂时没有违反 SLO，预算也消耗得过快，Burn Rate 可以提前反映这种风险。

**Fast Burn**

Fast Burn 指 Error Budget 在短时间内快速消耗，通常意味着突然发生严重故障或版本回退，例如：

```text
刚发布新版本
↓
大量 500 错误
↓
10 分钟消耗掉大量 Error Budget
```

**Slow Burn**

Slow Burn 的消耗速度较慢，但持续时间很长，例如：

```text
每天都有少量请求失败
↓
问题持续几个星期
↓
最终仍然可能耗尽 Error Budget
```

*关键词*

* **Error Budget**：允许的不可靠性额度。
* **Burn Rate**：Error Budget 的消耗速度。
* **Fast Burn**：短时间内快速消耗预算。
* **Slow Burn**：长期持续消耗预算。

Error Budget 反映还剩多少容错空间，Burn Rate 反映这部分空间消耗得有多快。

---

**8. Alert**

Azure Monitor 可以针对 SLI 配置不同类型的告警：

| 告警类型             | 通俗解释                      | 用途                   |
| -------------------- | ----------------------------- | ---------------------- |
| Baseline Alert       | SLI 已经低于 SLO              | 告诉你服务已经不达标   |
| Fast Burn Rate Alert | Error Budget 正在被快速消耗   | 提前发现突然恶化的问题 |
| Slow Burn Rate Alert | Error Budget 长时间持续被消耗 | 发现长期的小问题       |

三类告警关注的阶段不同：

```text
Baseline Alert：
“你已经不及格了。”

Fast Burn：
“照这个速度下去，很快就会不及格。”

Slow Burn：
“问题虽然不严重，但一直这样迟早会不及格。”
```

Burn Rate 告警能够在 SLO 真正被突破前发出预警，因此比只等待基线告警更早暴露风险。

---

### 整体流程

Azure Monitor 中创建和使用 SLI 的流程如下：

```text
确定要监控哪个服务
        ↓
选择 SLI 类型
Availability / Latency
        ↓
选择评估方式
Request-based / Window-based
        ↓
选择 Metrics
        ↓
通过 Filter / Aggregation / Formula
定义什么算 Good
        ↓
计算 SLI
        ↓
设置 SLO
        ↓
计算 Error Budget
        ↓
持续观察 Burn Rate
        ↓
配置告警
```

各概念之间的关系如下：

```text
SLI
实际表现
   ↓
与 SLO 比较
   ↓
SLO
目标表现
   ↓
100% - SLO
   ↓
Error Budget
允许失败多少
   ↓
Burn Rate
失败额度消耗多快
```

SLI 描述系统的实际表现，SLO 规定目标水平，Error Budget 表示还能容忍多少失败，Burn Rate 则反映这部分额度的消耗速度。
