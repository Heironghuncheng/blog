# 开源 PR 复盘

这篇记录三个 PR：Kinetic 的流式 logprobs 和 Phi-3 CPU 接入，以及 CodexPlusPlus 的 Agent 配置编辑。重点是问题怎么定位、改动怎么收敛，以及最后交付了什么。

# 第一部分：Kinetic

## PR #33：流式与非流式 logprobs 不一致

### 前置知识：SSE 与 WebSocket

在实现服务端实时推送时，最常见的两种方案是 **SSE（Server-Sent Events）** 和 **WebSocket（WS）**。

**SSE** 基于标准 HTTP 协议，是一种**单向流式传输**机制。客户端发起普通 HTTP 请求后，服务端在响应头中声明 `Content-Type: text/event-stream` 并保持连接不断开，随后将生成的数据分成多个 chunk，以纯文本（`data: ...\n\n`）的形式持续推送给客户端。它复用 HTTP 基础设施，天然兼容现有的代理、网关与负载均衡，浏览器原生 `EventSource` 也自带断线重连能力。

**WebSocket** 则是独立于 HTTP 之外的**全双工通信**协议。它先通过 HTTP 握手完成协议升级（`Upgrade: websocket`），之后在同一条 TCP 连接上，客户端和服务端可以随时互相收发文本或二进制消息。相比 SSE，它的协议开销更低、交互更灵活，但需要服务端和网关额外维护长连接状态，断线重连和心跳保活也需自行实现。

| 对比维度     | SSE                                | WebSocket                        |
| ------------ | ---------------------------------- | -------------------------------- |
| **通信方向** | 单向（服务端 → 客户端）            | 双向（全双工）                   |
| **底层协议** | 标准 HTTP                          | 独立协议（经 HTTP 握手升级）     |
| **数据格式** | 仅支持纯文本（UTF-8）              | 支持文本与二进制                 |
| **断线重连** | 原生支持                           | 需自行实现                       |
| **典型场景** | 大模型流式输出、实时日志、行情推送 | 即时通讯、协同编辑、多人在线游戏 |

大模型推理本质上是“一次请求、持续输出”的单向场景，客户端在生成过程中不需要反向发送数据，因此主流 API 普遍选择实现更轻量的 SSE。

### 问题描述

向 OpenAI 兼容接口 `/v1/chat/completions` 发两次请求，模型、提示词和停止条件都一样。当 `stream` 设为 `false` 时，关闭流式模式，服务端等生成结束后一次返回完整结果；设为 `true` 时，服务端边生成边发片段。我把流式片段拼起来，和非流式结果比较。

以 `stop: [" Paris"]` 为例。模型生成了 `The capital of France is Paris`，最后一个 token `" Paris"` 命中了停止条件，两边返回的正文都只剩 `The capital of France is`。两边的结束原因 `finish_reason` 都是 `stop`，`usage.completion_tokens` 也都是 6，因为 `" Paris"` 确实生成过。

差异出在随答案返回的 token 对数概率记录，也就是 `logprobs.content`。修复前，非流式返回 6 条，把正文里已经去掉的 `" Paris"` 也附了上去；流式拼起来只有 5 条。

Issue #31 的三个用例都用 `SmolLM2-135M-Instruct-f16.gguf`，并发送同一条用户消息：`What is the capital of France? Answer in one word.`。请求都设置 `temperature: 0`、`logprobs: true` 和 `top_logprobs: 1`。表格左侧是各用例的生成参数，右侧是对应的结果：

| `max_tokens` | `grammar`                                    | `stop`                   | 可见文本                     | `finish_reason` | `usage.completion_tokens` | 非流式条目 | 流式条目 |
| -----------: | -------------------------------------------- | ------------------------ | ---------------------------- | --------------- | ------------------------: | ---------: | -------: |
|           16 | 未设置                                       | `[" Paris"]`             | `"The capital of France is"` | `stop`          |                         6 |          6 |        5 |
|           16 | `root ::= "The capital of France is Paris."` | `[" capital of France"]` | `"The"`                      | `stop`          |                         4 |          4 |        1 |
|            3 | `root ::= "A🙂"`                              | 未设置                   | `"A"`                        | `length`        |                         3 |          3 |        1 |

`grammar` 是请求里的生成约束。每生成一步，推理引擎只允许模型选择符合规则的 token。后两个用例沿用同一条提示词，用规则 `root ::= "..."` 让模型按引号里的固定文本生成。`stop` 和 `max_tokens` 仍然可以提前结束生成。比如第三组的目标是 `A🙂`，但达到 3 个 token 时，`🙂` 的字节还没凑齐，所以只返回 `A`。

`usage.completion_tokens` 统计的是模型实际生成的总 token 数（包括被 `stop` 吞掉的 token 以及 EOS），看上去没有问题。差异都出在“生成了、但没有出现在返回文本里”的尾部 token 上。第一眼看过去，会以为是流式少发了。

### 复现流程

用修复前的 Kinetic（提交 `9b4844f`）启动服务。在 CPU 上加载测试用的小模型，只开一个并发槽，并关闭提示词缓存：

```sh
kinetic serve SmolLM2-135M-Instruct-f16.gguf --device cpu --parallel 1 --no-prompt-cache -c 2048
```

表里的每一行都发两次请求。两次用同一条提示词和同一组生成参数，分别请求非流式和流式响应：

1. 发非流式请求（`stream: false`），从完整 JSON 里取出正文、`finish_reason`、`usage` 和 `logprobs.content` 数组。
2. 发流式请求（`stream: true`），加上 `stream_options.include_usage: true` 取得用量。按顺序读取 SSE 的 `data:` 事件，把 `choices[0].delta.content` 拼成正文，把 `choices[0].logprobs.content` 的条目接成一个数组。另取结束事件里的 `finish_reason` 和用量事件里的 `usage`。`[DONE]` 只表示传输结束。
3. 比较整理后的两份结果。修复前，三个用例的正文、结束原因和用量分别一致，但非流式的 `logprobs` 都多出尾部条目。

在另一个终端运行下面的命令。每次调用 `compare` 都发送同一个用例的两种请求，并打印原始响应：

```sh
url=http://127.0.0.1:8080/v1/chat/completions
common='"messages":[{"role":"user","content":"What is the capital of France? Answer in one word."}],"temperature":0,"logprobs":true,"top_logprobs":1'

compare() {
  curl -sS "$url" -H 'Content-Type: application/json' -d "{$common,$1,\"stream\":false}"
  printf '\n'
  curl -sSN "$url" -H 'Content-Type: application/json' \
    -d "{$common,$1,\"stream\":true,\"stream_options\":{\"include_usage\":true}}"
  printf '\n'
}

compare '"max_tokens":16,"stop":[" Paris"]'
compare '"max_tokens":16,"grammar":"root ::= \"The capital of France is Paris.\"","stop":[" capital of France"]'
compare '"max_tokens":3,"grammar":"root ::= \"A🙂\""'
```

流式事件的边界不一定和 token 边界对齐，所以要等正文和数组都拼完再比较。

### 根因：两种模式对无可见文本的尾部 token 处理不一致

要理解这个 bug，首先需要明确 token、字节与字符并非一一对应。

单个 token 可能只包含部分 UTF-8 字符，解码器会先缓冲字节，等后续补齐后再输出完整字符。

在此基础上，`stop` 字符串是在解码后的文本上匹配的，命中时可能吞掉单个或多个 token；而 `max_tokens` 按 token 数量硬截断，若刚好停在多字节字符中间，解码器会直接丢弃这半截不完整的字符。

对应的三个测试用例，正好分别命中了三种“已生成但无可见文本”的尾部场景：整个 token 被 `stop` 吞掉；多个 token 拼接后被 `stop` 吞掉；字符被 `max_tokens` 截断，残余字节留在 token 里，解码输出为空。

Bug 的根源在于流式与非流式两条代码路径对这些“尾部无文本 token”的处理逻辑产生了分歧：非流式实现持有完整 token 列表，生成结束后直接全量返回；而流式实现只有在解码完成产出新字符并真正发出时才会附带 logprobs，一旦尾部没有可见文本可发，对应的 logprobs 条目便不会被发送，导致两边结果不一致。非流式多，流式少。

### 定位：响应组装与字段约定

直接看流式与非流式返回 logprobs 的函数即可。

非流式走 `complete_with_logprobs`，生成结束后拿到完整的 logprobs 列表，直接全部返回。流式走 SSE handler，每当拼出新的可见文本并打包成 chunk 发送时，才把暂存（pending）的 logprobs 条目一并附带发出；如果后面没有新的文本 chunk 可发，这些 pending 条目就不会发出。

可以看到，两种模式下推理引擎都保留了完整的生成记录。既然底层记录一致，问题就不在采样或内核计算，而在于**响应层如何筛选放进返回体里的条目**。

顺着这个定位，issue 里的方向就很明确：`logprobs` 只保留字节确实出现在返回文本里的 token，被 `stop` 删掉的、没拼完的残缺字符都不算有效输出。按这个标准，流式行为已经符合要求，需要修改的是非流式实现。

`logprobs` 跟随可见文本，`usage` 跟随生成过程。`usage.completion_tokens` 用于统计模型实际生成的 token 数量，不能为了对齐流式与非流式的 `logprobs` 数组长度而修改它。

### 修复：按可见字节裁剪 logprobs

PR #33 的做法并不复杂，核心思路是给生成的 token 建一份“字节账本”，用最终可见文本的字节边界去统一裁剪 `logprobs`，让流式和非流式走同一套逻辑。

**核心改动：`TextLogprobs` 按字节前缀裁剪**

1. **记录每个 token 的字节范围**：新增 `TextLogprobs`，在生成时顺手记下每个 token 对应的原始字节，以及它在整段字节流中的起始偏移（例如 Token 0 占 `0~3` 字节，Token 1 占 `3~9` 字节）。
2. **用可见文本边界截断列表**：当确定最终要返回的可见文本（或流式每次有新文本要发出）时，先算出这部分可见文本对应的字节长度 `N`，再用 `partition_point`（二分查找分界点）找出落在前 `N` 个字节内的 token，只保留这一段前缀的 `logprobs`。
3. **跨 token 截断的判定**：如果 `stop` 字符串刚好切在某个 token 中间（例如切在第 `11` 字节，而该 token 占 `9~14` 字节），只要它有部分字节进入了返回文本，就保留它的 `logprob`；只有完全没进可见文本的尾部 token 才会被裁掉。
4. **双端收口**：流式与非流式不再各自处理，统一走这条按字节前缀裁剪的路径。

**典型裁剪用例拆解**

下面用三个具体场景，对照 `TextLogprobs` 的字节账本说明 `logprobs` 是如何按可见字节边界裁剪的。

**用例一：整词被 `stop` 吞掉（`stop: [" Paris"]`）**

模型连续生成 6 个 token，拼接后为 `"The capital of France is Paris"`（共 30 字节）。`TextLogprobs` 记录各 token 的字节范围：

| Token   | 内容         | 字节区间  | 是否进入最终可见文本     |
| ------- | ------------ | :-------: | ------------------------ |
| Token 0 | `"The"`      |  `0 ~ 3`  | 是                       |
| Token 1 | `" capital"` | `3 ~ 11`  | 是                       |
| Token 2 | `" of"`      | `11 ~ 14` | 是                       |
| Token 3 | `" France"`  | `14 ~ 21` | 是                       |
| Token 4 | `" is"`      | `21 ~ 24` | 是                       |
| Token 5 | `" Paris"`   | `24 ~ 30` | **否（被 `stop` 删掉）** |

- **裁剪过程**：命中 `stop: [" Paris"]` 后，最终返回的正文为 `"The capital of France is"`（**24 字节**）。按 `24` 字节边界裁剪，保留起始偏移小于 `24` 的 Token 0~4（共 5 条），裁掉起始偏移为 `24` 的 Token 5。
- **效果**：非流式不再多返回第 6 条 `" Paris"` 的 `logprob`，与流式的 5 条一致。

**用例二：UTF-8 字符被 `max_tokens` 截断（`max_tokens: 3`，目标 `"A🙂"`）**

UTF-8 下的 `🙂` 占 4 个字节，生成 3 个 token 时尚未凑齐完整字符：

| Token   | 原始内容       | 字节区间 | 解码后状态           |
| ------- | -------------- | :------: | -------------------- |
| Token 0 | `"A"`          | `0 ~ 1`  | 输出 `"A"`           |
| Token 1 | `🙂` 前半段字节 | `1 ~ 3`  | 字节未拼齐，进入缓冲 |
| Token 2 | `🙂` 后续字节   | `3 ~ 4`  | 仍不完整，结束时丢弃 |

- **裁剪过程**：达到 `max_tokens: 3` 后，未凑齐的残缺 UTF-8 字节被丢弃，最终可见文本只有 `"A"`（**1 字节**）。按 `1` 字节边界裁剪，只保留起始偏移为 `0` 的 Token 0（**1 条**），Token 1 和 Token 2 均被裁掉。
- **效果**：非流式的 `logprob` 从 3 条收敛为 1 条，与流式一致。

**用例三：`stop` 切在 token 中间（`"helloworld"`，`stop: ["low"]`）**

假设模型生成 3 个 token，拼接后为 `"helloworld"`（共 10 字节）：

| Token   | 内容     | 字节区间 | 说明                                            |
| ------- | -------- | :------: | ----------------------------------------------- |
| Token 0 | `"hel"`  | `0 ~ 3`  | 完整落在可见文本内                              |
| Token 1 | `"lowo"` | `3 ~ 7`  | `"low"` 触发停止，但其后的 `"o"` 处于停止点之前 |
| Token 2 | `"rld"`  | `7 ~ 10` | 完全未进入可见文本                              |

- **裁剪过程**：`stop: ["low"]` 截断后，最终可见文本为 `"hel"`（**3 字节**）。按可见文本字节边界判定时，只要某个 token 有部分字节进入了返回文本，就保留它的 `logprob`；只有完全没进可见文本的尾部 token（如起始偏移在 `3` 及之后的 Token 1、Token 2，视具体切分边界而定；若边界设为 `4` 覆盖到 `"o"`，则 Token 1 保留、Token 2 裁掉）才被剔除。
- **效果**：裁剪依据始终是可见文本对应的字节范围，避免把完全不可见的尾部 token 误算进 `logprobs`。
- **设计原因**：裁剪 `logprobs` 的依据是“可见文本占了多少字节”。只要某个 token 有一部分字节落在了最终可见文本的字节范围内，说明它对可见输出有贡献，就留在 `logprobs` 列表里；反过来，如果整个 token 的起始位置就已经超出了可见文本的字节长度（一个字节都没进可见文本），就直接丢掉。

**测试验证**

测试分为单元测试和 HTTP 回归测试两层：

- **单元测试**：重点验证两个边界场景：

  1. **可见前缀恰好落在 token 中间**：当 `stop` 停止词切在某个 token 内部时，只要该 token 的前半部分字节已经进入最终可见文本，就必须保留它的 `logprob`；只有起始字节完全超出可见长度的尾部 token 才会被裁掉。
  2. **未凑齐的 UTF-8 字节与替换字符（`U+FFFD` / `�`）不计入可见长度**：多字节字符（如 4 字节的 `🙂`）尚未生成完整时，残缺字节会暂留在解码缓冲区中，部分解码状态下会表现为替换字符 `�`。测试验证裁剪逻辑不会被占位符或缓冲中的半截字节误导，只按真正已经落地的有效可见字节数截断 `logprobs`，避免把未拼出完整字符的尾部 token 多留下来。
- **HTTP 回归测试**（`chat_logprobs_after_string_stop` 和 `chat_logprobs_after_utf8_cutoff`）：先用 `grammar` 固定模型输出，拿到全量 `logprobs` 作为基准，再分别叠加 `stop` 字符串或 `max_tokens` 截断，最后断言流式拼接后的 `logprobs` 与非流式结果完全一致，且 `usage` 不变。

### PR #33 复盘

这次排查和修复最重要的是整套**差分定位与边界对齐**的工作方法。

- **先找“应该一致”的配对路径做差分**：推理服务里有很多天然应该行为对齐的组合，比如流式与非流式、单条与批处理、开启与关闭缓存、CPU 与 GPU。遇到表现异常时，先挑出一对“理论上应该一致”的路径，用同一组输入（尤其是 `stop`、`max_tokens`、多字节 UTF-8 字符这类边界输入）跑两边并对比输出，往往比从头盲读推理代码更快揪出差异点。
- **先确认协议与行为约定，再动手改代码**：输出不一致并不总是代码 bug，有时是接口协议没写死、或者不同路径原本就允许存在差异。先在 issue 里把现象和疑问说清楚，确认“这两边到底应该一致吗”，拿到维护者的明确口径后再定修改方案，能避免改出不符合预期的行为，也省去返工。
- **划清统计字段的职责边界**：像 `logprobs` 和 `usage.completion_tokens` 看似都和生成结果相关，但统计对象并不相同。修对齐问题时，先看清各自反映的是“可见输出”还是“实际生成消耗”，不要为了凑相同的数组长度去改错统计口径。
- **适合作为系统与协议层排障的切入点**：这类问题不需要碰底层采样或张量计算内核，重点在于理清协议语义、构造边界用例、观察响应层如何组装与裁剪数据。顺着输入、状态流转和输出结构一路对照下来，很容易建立起对服务端请求处理链路的整体感知。

## PR #39：Phi-3 CPU 接入

### 为什么选 Phi-3

修 #33 时，我主要看的是服务端怎么组装响应。合入后，我想再往里看一层，就打算亲手接个模型，弄明白 Kinetic 怎么把不同模型的结构接到同一套推理代码上。

本来想做 Qwen3-30B-A3B，起码这模型我听过。可一想到后面要一遍遍跑测试，30B 对我手头的条件还是太大了。没那金刚钻，就别揽那瓷器活。

我回头去翻仓库自己的 `docs/good-first-issues.md`，第 16 项正好是「Fused QKV weights (Phi-3 and others)」。Phi-3 Mini 4K 的官方量化文件小，可以在 CPU 上反复跑一致性测试。我当时想，换成这个小模型应该能比 Qwen3 少等不少时间，于是开了 #35，认领 Phi-3 的适配。

其实第 16 项已经写了从哪儿下手：先看 `arch/transformer.rs` 和 `loader.rs`，在加载时把融合的 QKV 权重拆成三份视图。验收也写得很清楚：Phi-3 的 GGUF 得能加载，贪心生成的前 32 个 token 得跟 llama.cpp 对上，还要通过 `architectures` 测试。我那会儿光想着小模型跑测试能省多少时间，没仔细看这几行。

#33 用过的 [SmolLM2-135M-Instruct](https://huggingface.co/HuggingFaceTB/SmolLM2-135M-Instruct/blob/main/config.json) 走的是 Llama 的加载路径，9 个 Q 头共用 3 组 K、V，每头 64 维。[Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B/blob/main/config.json) 则是 16 个 Q 头共用 8 组 K、V，每头 128 维，还会在算注意力前对 Q 和 K 做归一化。这两个模型都用分组查询注意力（GQA）。在 Kinetic 支持的 GGUF 里，Q、K、V 和 `gate`、`up` 都分开存，加载器可以直接按名字取。

### 前置知识：从 GGUF 权重到共享计算层

给 Kinetic 接一个新模型，主要对齐两件事：计算层怎么算，权重文件里的哪块数据交给哪一步。拿 Phi-3 来说，注意力这边要确认 Q/KV 头的分组和 RoPE 的通道配对，加载这边要解决两组融合权重的切分。

**注意力层：QKV、因果掩码与 KV Cache**

Transformer 每一层只有两大模块：注意力层（Attention）负责在不同 token 之间搬运、汇总上下文信息，前馈层（FFN）负责在每个 token 内部独立加工特征。

词义高度依赖上下文，最直觉的关联做法是直接拿两个词的向量算点积 \(x_i \cdot x_j\)，但这有三个问题：一个向量和自己的点积往往最大，注意力容易锁死在自身；点积对称，导致 A 关注 B 的程度被迫等于 B 关注 A（而语言里“它”需要看前文的“小猫”，“小猫”却不用看后面的“它”）；直接拿原词向量加权平均，会把目标词身上的无关属性一并带过来。因此注意力层用三套独立的权重矩阵 \(W^Q, W^K, W^V\)，把输入 \(x\) 投影成三个角色：Q（Query）表达当前词缺什么线索，K（Key）表达每个词对外挂着什么检索标签，V（Value）表达匹配上之后实际交出哪部分特征。这样就把“找谁”和“拿什么”拆开了。

标准缩放点积注意力的计算公式是 \(\text{Softmax}(\frac{Q K^\top}{\sqrt{d_k}} + M) V\)，按顺序拆成几步：

1. **相关性打分与缩放**：拿当前词的 Q 和上下文各词的 K 做点积，再除以 \(\sqrt{d_k}\)（\(d_k\) 是单头维度，Phi-3 Mini 为 96）。维度高时点积方差会放大，极端数值进 Softmax 容易饱和，梯度会掉到接近 0，除以 \(\sqrt{d_k}\) 能把方差拉回 1 附近。
2. **因果掩码（Mask）**：自回归生成模型必须满足时间上的因果顺序，第 \(i\) 个位置的 Query 只能查询位置 \(0\) 到 \(i\)（前面以及自己当前位置）的 K 和 V，不能偷看后面的未来词。做法是在 Softmax 前把未来位置（分数矩阵的上三角）填成 \(-\infty\)，过完 Softmax 后对应权重会直接变成 0。
3. **加权汇总与多头融合**：拿归一化后的权重去乘 V，把相关词的特征打包回来。为了同时捕捉语法搭配、代词指代等多种关系，模型把隐藏维拆成多个低维头并行计算（Phi-3 Mini 把 3072 维拆成 32 个 96 维的头），各自算完拼回 3072 维，再乘输出投影矩阵 \(W_O\)（GGUF 里对应 `attn_output.weight`）融合对齐，加回残差流。

因为有因果掩码，已经算过的历史 token 的 K 和 V 不会随新词加入而改变。推理引擎会把它缓存下来，即 KV Cache，并把推理分成两个阶段：Prefill（预填充）并行处理整段 Prompt，此时多个 token 同时计算，必须启用因果掩码，保证每个位置写进缓存的状态和逐字计算一致；Decode（逐字解码）每次只送入最新生成的 1 个 token，算出它的 \(q_t, k_t, v_t\) 并把 \(k_t, v_t\) 追加到缓存末尾，再拿 \(q_t\) 去查整块历史 KV Cache。因为这 1 个新词本身就在序列最末尾，不存在未来词，单 token 解码时不需要做掩码屏蔽。

**MHA 和 GQA：Q 头与 KV 头的分组比例**

多头注意力（MHA）里，每个 Q 头都有自己的一对 K、V 头。[分组查询注意力（GQA）](https://aclanthology.org/2023.emnlp-main.298/)让几个 Q 头共用一组 K、V。比如 32 个 Q 头配 8 个 KV 头，每 4 个 Q 头一组，各自算各自的注意力分数，但读同一份 K、V 缓存。注意力的点积计算次数其实没少，省下来的是 KV Cache 的体积，以及 Decode 阶段反复从内存读取历史 K、V 的带宽。在每头维度和精度不变的情况下，单个 token 要缓存的 K、V 数据量只剩 MHA 的四分之一。

头数比例直接决定融合权重从哪几行切。[Phi-3 Mini 4K](https://huggingface.co/microsoft/Phi-3-mini-4k-instruct/blob/main/config.json) 用的是 MHA：32 个 Q 头、32 个 KV 头，每头 96 维，`attn_qkv.weight` 里 Q、K、V 各占 3072 行，加载时刚好三等分。换成上面 32 配 8 的 GQA，Q 还是 3072 行，K 和 V 就各剩 768 行。切分逻辑得按 `[q_dim, kv_dim, kv_dim]` 算偏移，不能写死成均分。

**RoPE：按相对位置旋转 Q 和 K**

[原版 Transformer 的正余弦位置编码](https://arxiv.org/abs/1706.03762)是根据 token 位置算一个向量，直接加到词嵌入上。这么做会把位置信息和词义混在同一个向量里，经过线性投影后，点积里夹着一堆词义和位置的交叉项，模型只能靠训练自己摸索怎么还原相对距离。[RoPE（旋转位置编码）](https://arxiv.org/abs/2104.09864)不在输入端做加法，而是在算注意力前，按 token 位置把 Q 和 K 各自转一个角度。两个向量的点积只看模长和夹角。比如 Q 在第 7 位、K 在第 4 位，算点积时两边共同多转的角度会抵消，剩下的夹角差只取决于它们相隔的 3 个位置。把这两个词原样挪到第 107 位和第 104 位，算出来的点积完全一样，相对位置关系直接写进了点积运算里。

旋转要两个通道一组来做，因为高维空间里直接构造旋转矩阵开销太大，最简单的办法是把一个注意力头拆成若干个二维平面。比如 Phi-3 Mini 每头 96 维，两两凑成 48 对，每对看成二维平面上的坐标 `(x, y)`，按二维旋转矩阵各自转自己的角度。二维旋转不改变向量长度，不会把数值越乘越大；拆成多对后还能给不同平面分配不同转速。第 \(i\) 对通道每前进一个 token 旋转的角度是 \(\text{base}^{-2i/d}\)：第 0 对每步转 1 弧度，转得最快，用来区分相邻几个词的精细位置；越往后的通道对转得越慢，用来覆盖更长的距离。

公式里的底数 \(\text{base}\) 对应模型配置里的 `rope_theta`（在 GGUF 里叫 `phi3.rope.freq_base`，常被顺手叫作旋转基频）。它不是基础频率，而是决定各通道转速衰减的底数：\(\text{base}\) 越大，中低频通道转得越慢，单个旋转周期能覆盖的序列长度也越长。单靠旋转形式不能直接外推到超出训练窗口的长度，距离一旦超界，各通道组合出的角度会落进训练没见过的区间，长上下文模型通常需要调大这个底数把转速放慢，再继续训练或适配。Phi-3 Mini 4K 沿用的是 `10000.0`，Kinetic 要拿现成的权重复现推理结果，这个底数和位置编码方式都必须跟原模型对上。

**NeoX 和交错布局：通道的排列顺序**

每次挑两个通道凑成一个二维平面，具体挑哪两个，开源实现分成了两种排法。假设要一起转的两对通道是 `a, b` 和 `c, d`：NeoX 布局把向量对半拆开配对，内存里排成 `[a, c, b, d]`，配对下标是 `(0, 2)` 和 `(1, 3)`；交错布局把每对挨着放，排成 `[a, b, c, d]`，配对下标是 `(0, 1)` 和 `(2, 3)`。数学上转的是同样两对数，区别只在它们在内存里的摆放顺序。

Phi-3 用的是 NeoX 布局。如果权重按 NeoX 存，代码却按交错布局算，就会把不相关的 `a` 和 `c` 凑到同一个平面里转。此时张量形状没变，加载检查抓不到这个错，但注意力分数已经全算歪了，模型跑起来直接输出乱码。

**RMSNorm：归一化与 `eps`**

深层网络一层接一层，加上残差连接不断把前面层的输出往后累加，向量数值很容易越传越大，或者缩到接近零，训练时梯度不是爆炸就是消失。每层的注意力块和前馈块前面都要先做一次归一化，把激活值的尺度拉回稳定区间。

早期 Transformer 用的是 LayerNorm：先减掉向量均值，再除以标准差，最后乘一个学到的缩放权重 `weight` 并加上偏置 `bias`。后来实验发现，真正稳住数值的是按幅度缩放这一步，减均值和加偏置对大模型效果几乎没帮助，却要多扫一遍数据算均值、多存一份偏置参数。RMSNorm 干脆砍掉了减均值和 `bias`，直接拿输入向量的均方根（RMS）做除法缩放，再逐维乘上 `weight`。算得更快，访存更少，效果跟 LayerNorm 持平，现在主流大模型基本都换成了它。

以第 0 层为例，Phi-3 每层的两个缩放向量在 GGUF 里叫 `blk.0.attn_norm.weight` 和 `blk.0.ffn_norm.weight`。算均方根时为了防除零，开根号前要加一个小常数 `eps`，它来自元数据 `phi3.attention.layer_norm_rms_epsilon`（对应原配置的 `rms_norm_eps`）。这个值必须跟原模型对上，不能因为张量形状一致就随便填个默认值。

**前馈层：FFN、SiLU 与 SwiGLU**

注意力层汇总完上下文特征后，本质上只做了一次跨 token 的线性加权；紧跟在后面的前馈层（FFN）则逐个 token 独立加工内部特征，补齐非线性表达能力，同时占了模型约三分之二的参数量，承担主要的特征重组和知识检索工作。

这里不能省掉线性投影，直接对残差流做逐元素激活。残差流里混着前面各层不断累加的特征，方向是自由分布的，正负数代表不同语义。直接套逐元素激活函数，既没法让通道之间重新组合，还会死板地沿着坐标轴压制负半轴，迫使前面的网络在算语义的同时还得迁就坐标轴方向。先加一层可学习的线性投影，就把前后解耦了：前面只管把信息写进残差流，当前前馈层自己负责提取、重组特征再送进非线性变换。

至于为什么要先升维再降维，主要是为了兼顾表达能力和计算开销。把向量临时抬进更宽的高维工作区，能降低信息密度，防止过激活函数时信息塌缩，也更容易把低维里纠缠的特征拆开划分；加工完再压回原维度写回主干，既吃到了高维空间的容量和操作便利，又把整网的残差流、Attention 权重和 KV Cache 压在低维里，避免显存和带宽跟着膨胀。

传统前馈层分三步：单路线性升维、过激活函数、线性降维。激活函数早年常选 ReLU，负数一刀切归零，正数原样放行。它在零点有硬折角，负半轴梯度直接归零，容易出现神经元失活；多个 ReLU 叠加出来也只是分段折线，想拟合平滑曲线或特征乘积，只能堆很多神经元硬凑。现代模型普遍改用 SiLU（参数 \(\beta=1\) 时的 Swish，定义为 \(x \cdot \sigma(x)\)）：它在正半轴趋近于直线 \(y=x\)，负半轴不是硬截断，而是在 \(x \approx -1.28\) 附近轻微下凹一小段再贴近 0，整条曲线处处平滑可导，梯度回传更稳。

[SwiGLU（Swish-Gated Linear Unit）](https://arxiv.org/abs/2002.05202) 进一步把单路升维拆成了 `gate` 和 `up` 两条并行投影。原版 GLU（门控线性单元）用 Sigmoid 做门控激活，省掉偏置后的公式是 \(\sigma(x W_{\text{gate}}) \odot (x W_{\text{up}})\)；SwiGLU 把里面的 Sigmoid 换成 SiLU，算完再接降维矩阵 `down`，完整算式是 `down(SiLU(gate(x)) * up(x))`。单看 `SiLU(gate(x))` 只是“投影加激活”，真正让它变成门控的，是后面拿这组动态系数去逐元素乘 `up(x)`。

改成并行投影加乘法门控有几重好处：

- **直接造出二阶交互**：两条并行线性投影直接相加会退化成单个矩阵，换成逐元素相乘后，不加深网络就能直接表达输入特征之间的乘积交互，省下大量用来硬凑曲线的神经元。
- **把“算内容”和“控开关”拆开**：普通 FFN 里一套权重既要管通道开不开，又要算特征值，负数还会被裁掉。拆成两路后，`up` 专心算候选特征（正负都能保留），`gate` 专心按当前输入算出阀门系数，既能放行甚至放大负向特征，也能把无关通道压到接近 0，减少对残差流的串扰。
- **训练稳，推理也顺手**：`up` 分支不经过激活函数，反向传播时保留了一条线性梯度通路；两条并行投影吃的是同一份输入 `x`，互不依赖，推理时可以把两张权重拼成一张大矩阵，读一次 `x` 顺手把两路乘法一起算完。

因为多了一套投影矩阵，用 SwiGLU 的模型通常会把中间层维度 `n_ff` 从传统的 4 倍隐藏维收窄到三分之八，让总参数量和计算量基本持平。Phi-3 Mini 隐藏维是 3072，中间层刚好是 8192。落到 GGUF 文件里，`W_gate` 和 `W_up` 都是预训练学好的静态权重，Phi-3 把它们拼在了同一张 `ffn_up.weight` 中：名字里虽然只写了 `up`，实际前 `n_ff` 行存 `gate`，后 `n_ff` 行存 `up`。

**加载权重：GGUF 键名和按行切分**

模型转成 GGUF 时，张量名会按转换器的规范统一改掉，比如原模型里的 `model.layers.0.self_attn.qkv_proj.weight` 对应 `blk.0.attn_qkv.weight`。`arch/` 里的适配代码要做的事很直接：按 GGUF 键名取出张量、检查形状，再交给共享计算层。词嵌入 `token_embd.weight`（把 token ID 映成向量）和输出头 `output.weight`（给词表里每个 token 算出归一化前的分数 logit）由公共加载代码处理。如果模型绑定了这两份权重，GGUF 会省掉 `output.weight`，Kinetic 自动复用词嵌入；Phi-3 这两份是分开的。

融合权重能在加载时直接拆，靠的是 GGUF 的内存排布。线性层矩阵里每个输出分量占一整行，行内存放各个输入分量的权重（GGUF 将二维张量维度记为 `[输入维数, 输出维数]`）。量化块也沿行内的输入方向打包，比如 `Q8_0` 每 32 个数一块，`Q4_K` 每 256 个数一块。每块量化数据都在单行里闭合，按整行切分不会切断量化块。只要融合权重导出时本来就是按输出行拼接的，加载器用起始行号乘以单行字节数算出偏移，就能在原始数据上划出一段视图。后面拆 QKV 和 gate/up 用的就是这个办法，不需要复制内存，也不用提前反量化权重。

### 拆分融合权重：零拷贝行视图

对推理引擎来说，零拷贝可以省下加载权重时的内存和时间，Kinetic 也是这么做的。模型权重动辄几个 GB，加载时如果保留原始数据又整块复制，就得额外占用一份权重大小的内存；如果提前反量化，展开后的权重通常还会更大。实际实现里，Kinetic 用一段只读字节切片 `&[u8]` 引用原始权重。需要取一部分时，直接在这段字节上切出一个视图，就像 NumPy 切片返回 view 一样，不另开权重缓冲区，也不用先反量化。

在这个前提下，接入 Phi-3 碰到了一个格式对齐问题。Kinetic 现有的共享 Attention 和 SwiGLU 都假设权重是分开传的（Q、K、V 各占一张矩阵，`gate` 和 `up` 也各占一张），但 Phi-3 的 GGUF 文件把 Q、K、V 拼成了 `attn_qkv.weight`，把 `gate` 和 `up` 拼成了 `ffn_up.weight`。要接上这两边，做法无非两种：改共享计算层，让它直接吃融合权重；或者不动共享层，在 `arch/phi3.rs` 加载时把大矩阵拆成几段行视图传进去。我选了后一种，拆分逻辑全留在 Phi-3 自己的加载代码里，不影响其他模型。

能直接零拷贝切出视图，靠的是 Phi-3 的融合矩阵按输出行顺着拼。算线性层时，矩阵每一行对应一个输出分量，GGUF 按行连续存数据，量化块在单行内部闭合。几张矩阵沿输出行上下叠起来，行数变多但每行宽度不变，按整行切不会切断量化块；如果是按列左右拼，即使列边界碰巧对齐量化块，同一张子矩阵的数据也散在各行里，不能用一段连续的字节取出。另外，同样是上下叠行，有些实现会按注意力头交错存（头 0 的 Q、K、V 放一起，再放头 1 的 Q、K、V），那样 Q 的行在内存里是散的，切不出一段连续字节。Phi-3 是整块顺着排的，先把所有 Q 的行放完，再放所有 K，最后放 V；`ffn_up.weight` 也是先放完所有 `gate` 行，再放 `up` 行。同一张子矩阵的字节在内存里连成一片，才能直接借出一段连续的 `&[u8]` 切片。

落到代码里，切分靠四个接口配合：`Loader::matrix(name, cols, rows)` 按名字取张量，检查 GGUF 维度是不是 `[cols, rows]`（输入宽度在前，输出行数在后）；`Matrix::row_bytes()` 给出单行字节数，也就是行步长 `stride`；`rows()` 按 `[start * stride, (start + count) * stride)` 在原始字节上切片；最后 `Matrix::new` 包装子切片时再断言一次长度等于 `count * stride`。按这个规则，`attn_qkv` 被切成 `[0, d)`、`[d, d + kv_dim)`、`[d + kv_dim, d + 2 * kv_dim)` 三段视图，`ffn_up` 被切成前 `n_ff` 行和后 `n_ff` 行。

这套切法依赖融合矩阵按输出行顺着拼，且顺序是 Q/K/V 和 gate/up。偏移算错但切出的长度刚好一样，或者遇到按头交错、顺序相反的模型变体，形状和字节数检查都可能照样通过。我起初想补一条单元测试把偏移钉死：造一个小型量化矩阵，拿子视图逐行和原矩阵对应的行比字节，比如比 `rows(qkv, 0, d).row(r)` 和 `qkv.row(r)`，K、V 加上各自的起始行偏移后同理，`gate` 和 `up` 也照做。这能检查 `rows()` 有没有按指定偏移切，却抓不到加载器把 `gate` 和 `up` 接反，也识别不了实际 GGUF 里的排列变化。要查接反，得让加载器读一份布局已知的样本，再检查每路投影实际拿到的是哪段权重。

入门清单第 16 项原本写的是 `arch/transformer.rs` 和 `loader.rs`。写草稿时没动这两个公共文件，只在 `arch/phi3.rs` 局部拆视图。当时拿不准这合不合项目习惯，就在 Draft PR 里问过。11 月 27 日，维护者确认从 `attn_qkv` 和 `ffn_up` 借用行视图给共享层的做法合适。

### 边界检查：黑名单拒绝不支持的变体

草稿最初给 Phi-3 做了全张量白名单。后来我翻了维护者写的几个模型适配，发现 Llama 和 Qwen 共用的 `arch/transformer.rs`、BERT 用的 `arch/bert.rs` 都有一份 `UNSUPPORTED` 黑名单，遇到清单里的张量就报错。我就沿用了这个做法：必需张量还是要检查形状，已知不支持的张量和配置则明确拒绝。

两种做法各有取舍。白名单能发现未预料到的布局变化，文件里多出一个没见过的张量就会拒绝加载，哪怕它只是个无关的可选项。黑名单给这类可选张量留了余地，代价是没列出来的张量可能被跳过；如果它恰好会改变计算，文件能加载，结果也可能算错。

张量这边，Phi-3 的加载路径不读投影层的 `bias`，也不对 Q、K 额外做一次归一化，所以遇到相应张量就报错。`post norm` 也一样：这次接的是在 Attention 和 FFN 之前归一化的 Phi-3 Mini 4K，没有接入模块输出端的额外归一化。位置编码方面，`rope_freqs.weight` 是对各对旋转通道频率的额外调整，`rope_factors_long.weight` 和 `rope_factors_short.weight` 则是长上下文版本用的两套 LongRoPE 缩放因子。这次只接不缩放的 RoPE，这几张表都明确拒绝。

配置这边只接 4096 的上下文，先把 128K 等变体挡在外面。滑动窗口配置也会被拒绝：模型如果只该看最近一段 token，推理时就不能继续让它看到整个前缀。对 RoPE，加载器要求缩放类型为 `none` 或未声明，数值只接受 `0.0` 和 `1.0`。单头维度按 `隐藏维 / Q 头数` 算，Phi-3 Mini 就是 `3072 / 32 = 96`。如果 GGUF 显式声明了不匹配的 K、V 单头维度或 RoPE 维度，加载器会在切权重之前报错。

维护者看完 diff 后确认，新家族先按这个范围开始就合适。这版就保留了这份拒绝清单。

### 模板、分词与停止

模板这边，我用微软官方 GGUF 手动渲染了单轮和多轮对话，现有的 MiniJinja 路径直接可用，没有改模板代码。这一点挺省事，但也说明“模板能跑”和“模板正确”是两回事，至少要拿真实文件看一眼。

输入侧有一个 Phi-3 规则：大多数特殊 token 会吃掉紧跟的 ASCII 空白，例外是 `<unk>`、`<s>`、`<|endoftext|>`。我在 `b834e7a` 把这条规则和额外停止标记一起归到 tokenizer，在 `5912f54` 删掉中间的 `profile.rs`，最后按维护者的建议，在 `ff471ec` 把规则移到 `Tokenizer` 旁的 `FAMILY_RULES` 表。`Tokenizer::from_gguf()` 按 GGUF 架构查表；没列出的架构沿用默认行为。这次抽表没改规则和测试向量，实际的空白处理仍在 `spm.rs` 和 `special.rs`。

输出侧原来在 `engine.rs` 里按模型名追加 `</s>`。现在 `tokenizer.stop_tokens()` 返回 GGUF 声明的 EOS 和该家族需要的额外停止 ID，服务端不再为 Phi-3 单独判断。微软这份 GGUF 的 EOS 是 `32000`，模型仍可能吐出 `</s>`（ID `2`）。新单测验证 Phi-3 会返回两种候选，非 Phi-3 不会多出 `</s>`。

同步主分支后，我用同一份微软 Q4 GGUF 重跑了分词测试。把 GGUF 自动添加的 BOS 对齐后，54 条测试输入的 token ID 仍与 Hugging Face `tokenizers` 生成的参考 ID 一致。另外 8 条专门测特殊 token 后空白的输入，去掉自动添加的 BOS 后，Hugging Face、llama.cpp 和 Kinetic 的 token ID 也一致：`</s>`、`<|user|>` 和 `<|end|>` 后的换行会被吃掉，`<|endoftext|>`、`<unk>` 和 `<s>` 后的换行则保留。参考词表没有 GGUF 独有的 `[PAD...]` 补位项，我单独在 Kinetic 上确认了 `[PAD32011]` 后的换行也会被裁掉。

### CUDA：做了又撤

CUDA 最初的报错是每头 96 维不被接受，表面看像显存不够。原型补了短批分块和长提示的 Flash 路径，在本机 RTX 5070 Ti、另一台 RTX 3060 和一台 GTX 1660 SUPER 上跑过专项测试；还有一台机器卡在驱动初始化，没测成。

随后外部审阅指出：Kinetic CUDA 和 llama.cpp Vulkan 在第 5 个 token 分叉，参考侧前两名差 0.338 nat。改用同卡 CUDA 对 CUDA，仍在同一位置分叉，差 0.244 nat。两个数都超过仓库的 0.1 nat 近似平局阈值。

继续逐层排查：固定 token 后仍能复现；差异在进入 96 维 attention 之前就出现了；把 Kinetic 的首层 QKV 输出换进 llama.cpp CUDA，最终选择从 `That` 翻成 `Yes`；独立重算显示，两边量化缩放的精度不同，足以解释这个同卡样例；但只换首层 QKV 在 Vulkan 上没有翻转，所以结论不能跨后端套用，也不能据此宣布整个 CUDA 补丁正确。

最后决定：把整个 CUDA 目录撤回。这段是原型和诊断记录，不是 #39 的交付。11 月 28 日我用同时编入 CUDA 和 Vulkan 的新版再跑 `--device auto`：CUDA 报 `no layer fits on the device`，Vulkan 拒绝每头 96 维的注意力配置，最后回退到 CPU 并成功生成。这个结果验证的是回退路径。

回头想，这段“白干”其实最值钱。它让我第一次认真区分“能跑”和“对得上”：能跑只说明路径通了，对得上要说明数值一致。同卡对照比跨后端对照更有说服力；首层 QKV 替换是一个好的二分手段，但它只定位到“进入 attention 之前”，不证明整个后端正确。我最后没有把未验证的后端随 PR 发；诊断留在独立记录或 issue 里。

### CPU 复查：一个仍未对齐的 token

真实 GGUF 通过了 Kinetic 自己的四项架构一致性测试，包括批处理与逐 token 的 logits 对照、投机贪心与普通贪心的逐 token 对照。这组测试检查的是 Kinetic 自己的不同执行路径。下面和 llama.cpp 的对照回答的是另一个问题：同一份权重，两边会不会选出相同的 token？

线上 PR 正文还保留着早期每条最多生成 32 个 token 的三组对照，其中关 Flash Attention、用 F32 K/V 并关闭 repack 的那组按近似平局规则通过。11 月 28 日我用 Kinetic `0ebdcd1` 和 llama.cpp build `12806` 重跑。两边加载同一份微软 Q4_K_M GGUF，以 llama.cpp 的默认 CPU 设置作对照，每条最多生成 64 个 token。这里是这一轮的结果：

| 提示词 | 一致/对照 token 数 |
| ------ | -----------------: |
| 1      |               4/64 |
| 2      |              64/64 |
| 3      |              64/64 |
| 4      |              19/19 |

第一条在第 5 个生成 token 分叉（脚本里的索引是 `4`）：llama.cpp 选 `Yes`，Kinetic 选 `That`。llama.cpp 的前两名相差 `0.168 nat`，超过仓库的 `0.1 nat` 近似平局阈值，所以脚本退出 `1`。单独加 `--no-repack` 仍然分叉；关闭 Flash Attention 并改用 F32 K/V，也没有消掉这个差异。把 llama.cpp 的物理微批固定为 `1` 后，逐 token 解码和整段前缀的请求返回相同的 top-10，重复跑也一样，但两边还是各选各的。

接下来我固定住分叉前的 token，把同一份 Q4_K_M GGUF 反量化成 F32。这份文件保存的是原来量化后能读出的数值，没有找回量化前的权重。两边在这份文件上都选了 `That`，领先 `Yes` 的幅度分别是 `0.358898 nat`（llama.cpp，`--device none` 和默认微批大小）和 `0.355593 nat`（Kinetic）。保持 llama.cpp 的启动参数不变，只换成这份 F32 文件，它就从选 `Yes` 变成了选 `That`。

再往下试，在原 Q4_K_M 文件里只把第 29 层的 `blk.29.ffn_up` 换成它的 F32 反量化值，两边就都选 `That`。反过来，在其余权重已经反量化的版本里，只把这个张量换回 Q4_K，又不足以让两边分叉。换这一个张量能改变结果，但还不能断定是它的量化计算出了问题，还是上游传来的激活值和它一起影响了排序。我也还不能据此判断哪边更准。

# 第二部分：CodexPlusPlus

## PR #3186：Agent 配置编辑

今年 11 月，我一边准备实习，一边用 CodexPlusPlus 管理手头的各个 Agent。当时它推了一个默认走 WebSocket 连接的版本，我用起来却频繁提示断联，每隔几分钟就重连并丢上下文，当时整个人都快气炸了。我想着去改 `config.toml` 关掉供应商的 WS 支持，结果因为配置受 CodexPlusPlus 管理，改完之后一重启或切配置就容易被刷掉。我到处翻找编辑通用配置的入口却没找到，一查又没人改这块，一气之下就提了这辈子第一个面向公开开源项目的 PR，想把通用配置编辑放到一个顺手能找到的地方。回头看挺逗的，后来才发现就算改了通用配置也根本修不好那个问题，最初逼我动手折腾的默认 WS 断联，最后还是 CodexPlusPlus 自己改回默认 HTTP 才解决的。

事后看，我确实高估了自己。第一次改这么大的陌生项目，用的还是不熟悉的技术栈，中间几轮来回折腾，维护者没直接开骂已经算很客气了，我心里是真觉得过意不去。不过从结果来看，如果真嫌麻烦他大可以在第二轮就直接关掉；他愿意花时间一条条写出具体的冲突反例、指出哪些启动和切换路径不能碰，最后还顺手补上退出确认把代码合进主分支，大概在他眼里，我虽然一开始没收住改动边界，但反馈响应够快，也肯老老实实按评审意见重构并把测试补齐。这段合作经历本身，反而成了我参与开源最实在的收获。

### 为什么要加这个入口

在 [Issue #3016](https://github.com/BigPizzaV3/CodexPlusPlus/issues/3016) 里，有用户反映，手动在 `config.toml` 里改完权限，切一次供应商，刚改的值可能又变回去了。这里有两份配置：一份是 Codex 正在用的文件，另一份是 CodexPlusPlus 应用供应商时用的通用模板。只改当前文件，模板里的旧值还在。维护者建议把 `[permissions.*]`、`[sandbox_workspace_write]` 这类跨供应商的设置放进通用模板，MCP 则走专门的管理入口。我想补的是开启网关后「Agent 接入」页上的编辑入口，让用户从这页就能找到该改的配置。配置保留问题后来有[单独的修复](https://github.com/BigPizzaV3/CodexPlusPlus/issues/3016#issuecomment-7080358419)，多开和配置分层也没放进这个 PR。

### 初版：让所有 Agent 走一个弹窗

[我最初做的是一个通用弹窗](https://github.com/BigPizzaV3/CodexPlusPlus/commit/67e6b031)。点 `GatewayAgents.tsx` 里的 `AgentConfigButton`，`AgentConfigEditor.tsx` 就用 Tauri 命令 `read_agent_config` 读配置；点保存时，再用 `save_agent_config` 把草稿和打开弹窗时拿到的快照传给后端。前端只需要知道 Agent ID，两个命令都通过 `gateway/agents/editor.rs` 的 `config()` 确定读写哪个文件、开放哪些字段。

Codex 原本就有通用配置编辑器。我只想让用户从「Agent 接入」页也能找到它，把按钮接到原有编辑器就够了。我当时想着，既然做了弹窗，干脆让 Codex 也走这套。界面是更好看了，几个 Agent 的操作也一致了，可我连供应商详情里的旧编辑器都换掉了：`App.tsx` 的 `RelayFileEditors` 原来用 `SyncedTextarea` 编辑整份模板，换成 `AgentConfigButton` 后，用户只能改 `COMMON_KEYS` 里的 19 个键。

保存也重复造了轮子。`editor.rs` 的 `codex()` 把这 19 个键合并回 `relayCommonConfigContents`，再用 `ctx.settings.update()` 直接写入。`session_tuning.rs` 已经在写这些调优字段，我另写的这条路径却漏掉了原有的校验和供应商快照清理。点完保存，弹窗直接关掉，也没提示用户这次只改了模板，当前的 `config.toml` 不会立刻重写。回头看，这是初版最不该做的事：为了加一个按钮，把现成的编辑和保存都重做了一遍，还丢了原有功能。

我当时还想着一步做全，让 OpenClaw 和 Hermes 也能直接编辑。除了加 `editor_format.rs` 和四个依赖，我还在 `catalog_apps.rs` 里把 OpenClaw 的写入格式从 JSON 换成 JSON5，在 `catalog_tools.rs` 里改成按 YAML 子键记录 Hermes 由网关接管的配置。到这一步，连不打开编辑弹窗的用户，走原来的网关接入流程也会受影响。

### 第一轮评审：恢复完整模板，收窄 Agent 编辑

[第一轮评审](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#pullrequestreview-6007177108)里，维护者认可后端写文件的做法：由后端解析路径，保存前比对快照，写完再读回来核对。但他指出，我换掉旧编辑器后，用户还能点「提取当前供应商配置」，把权限段和沙箱段写进模板；这些段不在 `COMMON_KEYS` 里，写进去了却没法从界面改。他给了两种做法：把原来的完整编辑框留着，或者让新弹窗也能编辑整份模板。

[第一次返工](https://github.com/BigPizzaV3/CodexPlusPlus/commit/d4b6232b)时，我在 `App.tsx` 把供应商详情里的 `SyncedTextarea` 加了回来。「Agent 接入」页上的 Codex 按钮改为打开 `RelayCommonConfigScreen`，两处用同一个编辑组件，都能改完整模板。这样新按钮只是多了一个入口，原来能改的内容也还在。

保存这边，维护者建议复用 `session_tuning.rs` 的写入逻辑。我删掉了 `editor.rs` 里的 `codex()`，让前端改走 `save_settings`。模板有变化时，`aggregate_catalog.rs` 的 `save_with_catalog_publisher()` 会调用 `session_tuning::save_common()`，沿用调优字段的校验和供应商快照清理。这时保存只更新模板，不会立刻重写当前的 `config.toml`，也不会自动切换供应商。我在界面上补了提示，告诉用户重新应用或切换到使用通用配置的供应商后才会生效。

弹窗留给能单独开放偏好字段的 Agent，具体能改哪些字段由适配器声明。我在 `agents/mod.rs` 给 `AgentSpec` 加了 `preferences`，各个 `catalog_*.rs` 按自己的格式指定配置段和字段类型。比如 JCode 只开放 `[display]` 下的 `theme`。后端保存前仍会比对配置来源和可编辑内容，防止旧草稿盖掉别处刚做的修改；写入也只动允许编辑的字段，写完再回读确认。

维护者建议把网关格式改造和编辑入口拆开评审。我撤回了 JSON5/YAML 的网关改造和四个新增依赖，让 OpenClaw、Hermes 和 OMP 只显示配置来源。JSONC 继续用项目已有的 `jsonc_edit`，只补弹窗需要的偏好字段读写。

这一轮我确实在尽量按维护者说的范围往回收。我知道眼前哪些改动该撤，却没想清楚再碰到问题时该在哪儿停。后来发现删掉的配置值还可能被写回来，我又想着顺手修掉，没先问自己：这件事还该放在加编辑入口的 PR 里吗？

### 第二轮评审：把切换链路留在外面

准备二审时，我发现只清理供应商快照还不够。从模板里删掉一个调优值后，当前的 `config.toml` 依然留着旧值；如果这时直接切走，`relay_switch.rs` 会从当前文件提取配置，把刚删掉的值又存回快照。

为了修掉这个问题，我在 `session_tuning.rs` 里加了 `PendingBackfill`，让 `settings.rs` 用 `_relayTuningBackfill` 记下待处理项，在切换和重新应用时检查它。后来连 `launcher.rs` 的启动流程和 `commands.rs` 的重新应用也接上了 `with_template_reapply()`。原本只想防止一个旧值被写回来，最后连启动链路也改了。

同一版里我还动了几处公共逻辑：为了解决多行 `developer_instructions` 中的 `[表头]` 被误拆的问题，改了 `relay_config.rs` 里的 `normalize_duplicate_toml_text()` 以及配置段的拆分与合并；为了同步草稿，在 `App.tsx` 加了全局的 `rebaseConfigDraft()` 和 `acceptExternalSettings()`；还改了 `save_settings`，让它不再按旧规则迁出 MCP、技能和插件配置。

[第二轮评审](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#issuecomment-7080366712)里，维护者先确认一审的六点基本都处理完了，接着把这个 PR 能留下的范围列得很具体：后端的 `editor.rs` 和 `AgentSpec.preferences`，前端的 `AgentConfigDialog` 和通往完整模板页的 Codex 入口，加上 `jsonc_edit` 里为偏好编辑补的函数和对应测试。模板保存后提示用户重新应用就行，不用在保存时替用户应用。

该撤的地方，他也直接点到了函数和行号。`save_settings` 原来会自动迁出 MCP、技能和插件配置，这一版却直接拒绝包含这些内容的草稿，应该恢复旧行为。至于回填、启动时的冲突处理、公共 TOML 逻辑和前端全局设置同步，他建议分别另开 PR。多行 `developer_instructions` 被误拆确实是个问题，但这块代码所有写 `config.toml` 的路径都在用；他还指出排序里一处 `saturating_sub(1)` 会让多个供应商配置表算出同一个位置，因此这块需要单独评审并补上升级兼容测试。

启动那一块，他连出错的触发条件都捋清了：如果当前供应商正好有待回填记录，后台又恰好刷新了 token，设置版本就会变化；`with_template_reapply()` 遇到版本不一致会返回 `settings_revision_conflict`，启动流程收到这个错误就会直接退出。哪怕以后单独做这块，也得重读设置再试，或者让回填失败时不阻塞启动。

一审时他已经划过一次边界，二审这版还是没收住。维护者不得不顺着新加的代码一路看到启动和切换，逐处指出哪些能留、哪些得拆，连拆出去以后该防什么、该补什么测试都列了出来。这些范围和边界，本来应该在提交前就自己理清。

[这次返工](https://github.com/BigPizzaV3/CodexPlusPlus/commit/469cd2cb)时，我撤掉了整套回填机制，把启动和切换流程恢复原样；同时删掉 `save_with_catalog_publisher()` 转到 `save_common()` 的分支，撤回 `relay_config.rs` 的改动，让 `save_settings` 恢复原有的迁出行为。

防止旧草稿覆盖新配置这件事，我改成了只在模板页里处理。撤掉 `App.tsx` 的全局草稿同步后，`saveCommonTemplate()` 会先调用 `gateway_commands.rs` 里的 `read_relay_common_config(draft)`，校验 TOML 并读出最新设置；确认模板没被别处改过，才带着 `expectedRevision` 去调原来的 `save_settings`。如果保存时版本又变了，就保留草稿交给用户处理，不拿新版本号自动重试旧内容。这一版的读取命令只做校验和读取，还不负责清理快照。

### 第三轮评审：适配拆分后的主分支

11 月 23 日，[维护者确认](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#pullrequestreview-6023034813)前两轮的主要问题已经处理完，同时在评论里提到了 rebase。起初我以为只是随口一提，后来才意识到他的意思是确实得先同步主分支。当时上游刚拆了 `App.tsx`，冲突里有一大块是拆分前的旧代码，直接保留会把上游已经搬走的实现带回来。[这次同步](https://github.com/BigPizzaV3/CodexPlusPlus/commit/ac01f565)时，我丢掉了那块旧代码，把 `RelayCommonConfigScreen` 和 `SyncedTextarea` 一起留在 `RelayEditor.tsx`，并在 `App.tsx` 保留 `routeRef` 和 `setRouteState`；网关侧沿用 `GatewayAgents.tsx` 新的 `embedded` 布局和弹窗，只通过 `OpenAgentConfig.Provider` 把编辑按钮接进去。

除了解决冲突，维护者还建议在保存模板时调用已有的 `forget_snapshot_copies()`，并指出 `read_relay_common_config()` 不该在主线程同步读设置。我按要求把它标成了 `#[tauri::command(async)]`。带草稿调用时，`session_tuning::forget_changed_template_copies()` 会先比对新旧模板，再把改过或删掉的调优字段交给 `forget_snapshot_copies()`。例如模板删掉 `tool_output_token_limit = 4000` 后，使用通用配置的供应商快照里同为 `4000` 的副本会被清掉，供应商单独设的 `9000` 则不受影响。我用这两个值在 `tests/all/session_tuning.rs` 补了回归测试，同时确认不使用通用配置的供应商不会被改动。读取命令本身不负责落盘，处理后的快照会随新模板一起交给 `save_settings`。

不过，只靠保存时清理快照，还是解决不了那个边界问题：如果用户保存后没重新应用就直接切走，供应商切换仍可能从当前的 `config.toml` 把旧值存回快照。二审撤掉的回填机制没有再加回来，这里我选择不再强修，直接在 [PR 回复](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#issuecomment-7106737917)里把这一残留情况写清楚。

### 第四轮评审：同步主分支，复用已有组件

11 月 25 日，[维护者确认](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#issuecomment-7165581402)后端编辑器这边没问题了，他在本地跑的相关 Rust 测试也过了。不过主分支刚换成两步启动向导，和我这边的改动又有冲突，得再 rebase 一次。和第三轮一样，他把冲突挨个列了出来。光是 `App.tsx` 就点了四处，连 `preloadLazyPages` 和 `<section>` 新加的布局类都说到了。翻译测试该怎么接也写了：新版不再扫 `AgentFocusDialog`，把 `AgentConfigEditor.tsx` 加进文件列表就行。

这次同步到 `e012af63`，我在 `App.tsx` 里沿用主分支的新导航和扩展页布局，没有把上游已经删掉的 `AgentFocusDialog` 和 `closeAgentFocus` 带回来。`onboarding-i18n.test.ts` 也照他指出的地方改了。解完冲突我还漏了两处，后来[单独补了一个提交](https://github.com/BigPizzaV3/CodexPlusPlus/commit/aaefd34a)。布局测试要求 `<section>` 的第一个属性是 `className`，我就把它挪回第一位。主分支的 `i18n-en.ts` 已经有「编辑配置」，我删掉了自己重复加的那条。

弹窗这边，我之前在 `AgentConfigEditor.tsx` 里用 `useEscapeLayer` 和 `useModalFocus` 自己拼了一套。维护者让我换成现成的 `useModalShell`，让 Esc 和焦点行为跟网关里其他弹窗一致。两个编辑入口等配置时都用 `CxLoading` 的骨架，他还特地说别只放一行「正在读取…」。

[我按他的意见改了](https://github.com/BigPizzaV3/CodexPlusPlus/commit/22e10c19)：点击遮罩和关闭按钮都交给 `useModalShell` 处理。`AgentConfigDialog` 和 `RelayEditor.tsx` 里的 `RelayCommonConfigScreen` 在等配置读回来时都显示 `CxLoading`，读失败就显示错误。我也在 `agent-config-editor.test.ts` 里补了测试，确认加载提示会出现也会消失，标题和弹窗正确关联，保存时点遮罩不会把弹窗关掉。

看到他又把冲突和改法写到这么细，我读着感觉他多少有点无奈。前两轮是我没把范围收住，让他多花了不少时间。到了第四轮，连该复用哪个现成组件还得他来提醒。我后来在 PR 里跟他道了歉，也说这个 PR 不再加新改动。

### 验证和合入

最后在本地跑前端测试时，有两项直接匹配源码文本的测试没过。查下来是 Windows 检出时把 CSS 的换行转成了 CRLF。我只把本机的换行改回 LF，确认文件和 Git 索引一致，没动测试，也没把 CSS 带进提交。最后前端测试过了 2,523 项，跳过 15 项。TypeScript 检查和 Vite 构建也过了，Rust 这边单独跑的 `gateway_agents` 和 `session_tuning` 分别过了 15 项和 5 项。

[维护者试合后确认](https://github.com/BigPizzaV3/CodexPlusPlus/pull/3186#issuecomment-7169019758)没有冲突，前端测试和 core、manager 的 Rust 测试也都通过了。合入时，[他还亲手帮我补了退出确认](https://github.com/BigPizzaV3/CodexPlusPlus/commit/4d375a85)。我漏掉了用户改完配置没保存就退出的情况。Agent 弹窗把草稿的 `dirty` 状态传给 `useModalShell`；模板页则用 `onDirtyChange` 告诉 `App.tsx` 还有未保存的修改。这样返回列表或从侧栏切到别的页面时，也会先问用户要不要放弃草稿。PR 最后在 2026 年 11 月 26 日 01:06（UTC+8）合入，合并提交是 `b44cc76f`。

看到他在合入回复里说还顺手补了一处，来回改了四轮，最后还得他亲自帮我收尾，他这下怕是彻底无奈了。

### 复盘：先把改动范围想清楚

回头看这四轮评审，返工最直接的原因，是动手前没把相关链路看全。我以前没维护过这么大的项目，改代码时只顺着编辑弹窗看到了怎么读和存模板，没接着往下追：重新应用和切换供应商时谁还会写 `config.toml`，程序启动时又会在什么时机读这些设置。因为视野只停在眼前这一块，初版和二审时我把替换旧编辑器、改网关写入格式、往启动链路加回填机制、修公共 TOML 拆分、调整 `save_settings` 迁出规则这些改动一股脑塞进了同一个 PR。在我看来只是把相关问题顺手一起修了，落到维护者面前的 diff 里，却意味着为了加一个入口，他得把启动、切换、配置解析和全局设置同步全部重新审一遍。

这次踩得最深的坑，是没有区分「本次必须解决的问题」和「顺带发现的边界问题」。二审前发现从模板删掉的调优值在切供应商时还会被写回快照，我下意识觉得既然撞见了就得修干净，结果加出来的 `_relayTuningBackfill` 一路伸进 `relay_switch.rs` 和 `launcher.rs`，反而引出了后台刷新 token 触发 `settings_revision_conflict`、直接把启动流程卡死的新风险。反观三审时的处理就稳妥得多：调用已有的 `forget_snapshot_copies()` 处理保存时的快照清理，至于保存后不重新应用就切换的残留边界，不再硬改主链路，直接写进 PR 回复里说明。对开源协作来说，把已知限制坦诚交代清楚、留给后续单独的 PR，远比在当前改动里塞进一个未经充分评估的补丁要安全。

另一个明显的问题，是动手前没先把仓库里已有的实现摸透，习惯性自己另起炉灶。后端这边，`session_tuning.rs` 原本就有完整的调优字段校验和快照清理，项目里也现成有 `jsonc_edit`，初版却在 `editor.rs` 里重写了一套 `codex()` 直接落盘，还新引了四个依赖去动 OpenClaw 和 Hermes 的格式，既重复造了轮子，又把原来能编辑整份模板的 `SyncedTextarea` 砍成了 19 个固定键。前端这边也一样，自己用 `useEscapeLayer` 和 `useModalFocus` 拼弹窗、顺手写一行读取提示，看似省了翻代码的时间，实际上漏掉了项目用 `useModalShell` 和 `CxLoading` 统一收口的交互规范。连草稿未保存时的离开确认，原本也是 `useModalShell` 配合 `dirty` 状态就能接上的能力，最后还得维护者在合入时亲手帮我补齐。成熟项目里的公共封装往往藏着很多之前踩坑攒下来的边界处理，照着同类页面和现有接口写，比自己重写一套省心得多。

前两轮把范围铺得太开，还带来了另一个隐性成本：战线拉长以后，主分支不会停下来等我。审到第三、四轮时，上游已经先后拆了 `App.tsx`、换了两步启动向导、删掉了 `AgentFocusDialog`。每次 rebase 都得重新理清上游的结构变化，稍不留神就会把已经删掉的旧代码带回来，还得处理布局属性顺序、重复的翻译键、Windows 检出把 CSS 换行转成 CRLF 这类仓库细节。把第一次提交的改动面收窄、尽早合入，不只是替维护者省精力，也是给自己少找解冲突的麻烦。

下次再改这类大型项目，我会先做两件事再写代码：一是把涉及读写的上下游路径从头到尾走一遍，弄清楚哪些模块属于主链路、这次坚决不动；二是找仓库里同类型的页面和后端命令看一遍，能复用的组件、状态和校验逻辑直接复用。等改完准备提交，先通读一遍完整 diff，拿一个问题卡死边界：一个从来没点过新按钮的用户，原来能做的事会不会也变？只要改动波及启动、切换、公共解析或者已有用户的写入格式，哪怕顺手就能改完，也应该拆出去单独评审。最后两千多项测试全过，也只说明测到的断言没挂，覆盖不到隐性交互和范围失控，这个判断只能靠开发者自己在提交前把住。
